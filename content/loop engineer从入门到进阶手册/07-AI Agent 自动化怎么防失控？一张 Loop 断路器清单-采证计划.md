## 已经足够支撑的论点

### 论点 1：没有可验收目标，Loop 会发散

可用证据：

- 第 5 篇明确区分坏目标和好目标。
- 好目标需要具体、可测试、有边界。
- `checklists.md` 也要求目标能用一句话描述，并且成功标准可验证。

可写成的读者获得感：

- 给读者一张“目标能不能进 Loop”的验收卡。
- 让读者先过滤掉“优化一下”“让项目更稳定”这类大目标。

### 论点 2：没有 state file，Loop 容易丢状态

可用证据：

- 第 5 篇提出 `TODO.md` state file，用来记录 Candidate Issues、Current Attempt 和 Log。
- `templates.md` 提供了通用 state file 模板。
- `loop-builder` 真实验证报告也把验证状态写入 `validation` 文件。

可写成的读者获得感：

- 给读者一个最低可用的 `TODO.md` 模板。
- 告诉读者状态应该放在模型外，而不是只放在聊天上下文里。

### 论点 3：第一轮必须只读侦察

可用证据：

- 第 5 篇第 3 步明确要求先跑只读侦察 Loop。
- 只读侦察的输出包括失败信号、相关文件、推荐修复范围、验收命令和适配判断。
- `checklists.md` 的成本控制也强调先跑只读侦察，再决定是否进入执行。

可写成的读者获得感：

- 把“先看清问题”作为第一个断路器。
- 让读者避免一上来就让 Agent 修改文件。

### 论点 4：Maker 和 Checker 必须分工

可用证据：

- 第 5 篇明确把 Maker 和 Checker 分开。
- Maker 只做最小修复，Checker 只做只读验收。
- 第 4 篇已经讲过 Planner / Generator / Evaluator 三角色闭环，可以作为方法论补充。

可写成的读者获得感：

- 给读者一套“干活的人”和“验收的人”的最小分工。
- 把 Checker 设计成专门检查范围、测试、风险和人工确认节点的角色。

### 论点 5：Loop 必须有停止规则

可用证据：

- 第 5 篇给出 CI 修复 Loop 的四个断路器：连续失败上限、单次运行时长、改动范围、人工确认。
- `checklists.md` 的断路器清单补充了范围扩大、修改测试、敏感动作、验收命令缺失、状态失真、成本超限等场景。

可写成的读者获得感：

- 直接提供一张“触发即停”的断路器清单。
- 让读者知道 Loop 的重点不只是跑起来，还要知道何时停。

### 论点 6：成本本身也是断路器

可用证据：

- 第 5 篇的成本管控部分说明 Maker、Checker 和失败重试会快速增加 token 消耗。
- `checklists.md` 提供最大轮次、最大时间、最大 token 或 API 成本等预算项。
- `loop-builder` 验证报告也记录了输出偏长、需要轻量档位的问题。

可写成的读者获得感：

- 给读者一个低成本起步原则：先慢后快、先只读再写入、限制候选数量和文件范围。
- 把成本预算写进 state file，而不是事后才看账单。

### 论点 7：人工确认是安全边界

可用证据：

- 第 5 篇要求 merge 前必须 review，遇到支付、权限、数据删除、生产配置时停下来交给人。
- `templates.md` 有人工确认清单，覆盖 merge、生产配置、权限、支付、数据删除、公开发布、商业上架等动作。
- `checklists.md` 的 Human3.0 对齐检查强调人保留最终判断权。

可写成的读者获得感：

- 给读者一张“哪些动作必须交给人”的清单。
- 明确 Agent 可以准备证据，但不能代替用户做最终判断。

## 断路器清单草案

| 断路器 | 触发条件 | 立刻动作 | 对应风险 |
|---|---|---|---|
| 目标断路器 | 目标无法写成 checklist | 停止，改成一次性 Planner 或人工拆解 | 任务发散 |
| 反馈断路器 | 没有测试、日志、评分表或用户确认方式 | 停止，只做分析 | 自我确认 |
| 只读断路器 | 第一轮需要直接写文件 | 改为只读侦察 | 范围失控 |
| 轮次断路器 | 同类失败连续 2 次 | 停止并写失败报告 | 重复烧成本 |
| 时间断路器 | 单次运行超过预算 | 停止并摘要当前状态 | 长时间卡住 |
| 范围断路器 | 从单文件扩大到多模块 | 停止，等待用户确认 | 顺手重构 |
| 测试断路器 | 需要改测试来通过 | 停止，要求人工确认 | 迎合结果 |
| 权限断路器 | 涉及权限、支付、数据删除、生产配置 | 停止，输出风险清单 | 越权操作 |
| 状态断路器 | state file 与真实 diff 不一致 | 停止，重新对账 | 上下文污染 |
| 成本断路器 | token、时间或 API 成本超预算 | 停止，缩小任务 | 投入失控 |

## 风险点

### 风险 1：标题承诺过大

“防失控”容易让读者以为有一套完整安全系统。正文需要明确：这篇提供的是最小断路器清单，不承诺解决所有 Agent 风险。

处理方式：

- 开头直接说适用范围：个人开发者、内容创作者、小项目维护者的第一个 Loop。
- 不写企业级安全治理。

### 风险 2：内容和第 5 篇重复

第 5 篇已经讲了 CI 自动修复实战。T1 必须把重点放到“停止规则和边界”，不要重新讲完整 CI 流程。

处理方式：

- 第 5 篇作为案例来源。
- 新文重点写断路器、场景、清单。

### 风险 3：变成纯清单，缺少故事

如果只列 10 条规则，收藏价值有了，但阅读动力不足。

处理方式：

- 用一个最小失控场景开头：Agent 修一个测试，结果改测试、扩大范围、连续失败、成本变高。
- 每个断路器都配一句具体场景。

### 风险 4：工具能力混写

这篇可以面向 Codex、Claude Code、Cursor、自建 Harness 的读者，但不能把某个工具的具体命令混到另一个工具里。

处理方式：

- 正文讲通用断路器。
- 具体命令只放 Codex 示例，其他工具只说按各自环境落地。

## 建议正文结构

```md
# AI Agent 自动化怎么防失控？一张 Loop 断路器清单

## 开头：一个小 Loop 是怎么跑偏的

用 200 字讲一个场景：修一个失败测试，Agent 连续重试、改了测试、扩大文件范围、最后人不知道该不该合并。

## 第一部分：Loop 失控通常不是模型突然变坏

讲 4 个根因：
- 目标不可验收
- 没有外部反馈
- 没有状态文件
- 没有停止规则

## 第二部分：10 个断路器

每个断路器都按这个格式写：
- 触发信号
- 立刻动作
- 为什么
- 最小提示词

## 第三部分：第一版断路器怎么落地

给一个 `TODO.md` 片段：
- 最大轮次
- 最大时间
- 允许修改范围
- 人工确认节点

## 结尾：先让 Loop 学会停，再让它跑得更远

引导留言：
- 你最担心哪种失控？
- 你想看 Codex、Claude Code、Cursor 还是内容生产 Loop 的断路器版本？
```
