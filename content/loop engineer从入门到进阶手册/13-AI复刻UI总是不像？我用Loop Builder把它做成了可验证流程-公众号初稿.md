# AI 复刻 UI 总是不像？我用 Loop Builder 把它做成了可验证流程

> Loop Engineering 从入门到进阶手册 · UI 复刻实战篇

这次的问题很具体。

一开始，我走的是最直觉的路线：

直接让 Codex 根据提示词生成一个 UI。

结果不太行。

页面能生成，但设计感、层级、密度和细节都不稳。你继续补提示词，它也会继续改，可每一轮都像在重新猜你的审美。

后来有一天，我的 AI 情报流里出现了一条线索：OpenClaw 作者发推提到，可以尝试先用 imgGen 生成设计图，再让编程 Agent 去实现。

这给了我一个新思路。

别让 Codex 同时负责“设计”和“实现”，先把目标视觉稿做出来，再让它进入更明确的还原任务。

于是我先用 imgGen 生成了一张 UI 视觉稿，然后让 Codex 按照这张图去复刻页面。

页面能做出来。

但看起来就是不对。

布局比例差一点，间距差一点，字体层级差一点，卡片质感差一点。每一处单独看都不算大问题，合在一起就会变成另一种风格。

继续补提示词也能改。

但很快会进入一种熟悉的拉扯：

- 让它调小间距，它顺手改了布局。
- 让它靠近目标色，它又把层级做平了。
- 让它对齐卡片，它把整体节奏弄散了。
- 你说“还是不像”，它会继续猜，但猜的方向未必对。

这就是 AI 复刻 UI 最难受的地方。

你从“没有设计稿，只靠提示词让 AI 生成 UI”，进化到了“有目标图，让 AI 照图复刻”。

但如果工作流还是普通 Prompt，任务仍然很容易变成一轮又一轮的口头修补。

这篇只讲一个问题：

**如何把 UI 复刻从“凭感觉改”，变成“目标图 -> 当前截图 -> 差异清单 -> 修 Top 3 -> 再截图验证”的闭环。**

## 问题不在提示词长度

UI 复刻和普通功能开发不一样。

功能开发可以用“按钮能不能点击、接口有没有返回、测试能不能通过”来验收。

UI 复刻要看布局、比例、颜色、字体、留白、阴影、圆角、图标、图片位置、组件密度和页面节奏。这些东西很难靠一句自然语言完整描述。

你可以把提示词写得很细：

```text
请尽量高保真复刻这张 UI 视觉稿，注意布局、字体、颜色、间距、圆角和阴影。
```

但 Agent 还需要知道更具体的执行反馈：

- 哪个差异最影响相似度？
- 这一轮优先改哪 3 个点？
- 改完以后有没有截图证据？
- 上一轮修正是否真的让页面更接近目标？
- 什么时候该停下来让人判断？

如果没有这些反馈，AI 很容易进入“继续改”的状态。

一次性 Prompt 的流程通常是：

```text
描述目标 -> AI 实现 -> 人眼觉得不像 -> 继续描述
```

Visual Match Loop 要补上的是硬反馈：

| 缺失环节 | 普通 Prompt 的表现 | Loop 的做法 |
|---|---|---|
| 目标拆解 | 直接写页面 | 先拆结构、组件树、设计 tokens |
| 反馈信号 | 人说“还不像” | 用目标图和当前截图生成差异清单 |
| 修正节奏 | 一次性大改 | 每轮只修 Top 3 差异 |

这套流程不追求 AI 一次命中，它要求每一轮都更接近目标，并且知道为什么继续、为什么停止。

---

## 这个场景为什么适合 Loop

并不是所有任务都值得上 Loop。

有些任务一次 Prompt 就够了，比如：

- 生成一个函数。
- 起草一段说明。
- 改一个很明确的小样式。
- 把一段代码解释清楚。

UI 复刻更适合 Loop，因为它同时具备四个条件。

**有明确目标样本。**

这次目标图来自 imgGen 生成的 UI 视觉稿。它比一句抽象需求更硬，因为它是一张可以反复对照的视觉样本。

**有可观察反馈。**

Codex 实现页面后，可以运行项目并截图。当前截图和目标图放在一起，就能看到差异。

**差异可以拆解。**

视觉差异不是只能靠感觉。它可以拆成布局、颜色、字体、间距、圆角、阴影、图标、图片、组件状态。

**有停止规则。**

当关键差异收敛、剩余问题进入主观审美区，或者连续两轮同类问题没有改善，就该停下来交给人判断。

这四个条件放在一起，UI 复刻就不再只是“让 AI 照着图写页面”。

它可以被设计成一个循环：

```text
目标视觉稿
-> 设计拆解
-> 分区实现
-> 页面截图
-> 差异评估
-> 修 Top 3
-> 再截图
-> 达标或停止
```

## 用 loop-builder 搭出闭环

如果每次 UI 复刻都手写目标、输入、验收标准、禁止动作和停止规则，启动成本依然很高。

`loop-builder` 要解决的就是这一步：**把一句模糊任务，整理成可确认、可执行、可停止的 Loop 工作逻辑。**

你可以只给它一句话：

```text
帮我复刻这个 UI 视觉稿。
```

它不应该马上生成执行 Prompt，也不应该开始读项目、截图或改代码。正确流程是：

```text
一句话任务
-> 判断缺什么关键上下文
-> 输出任务卡
-> 输出工作逻辑确认卡
-> 用户确认
-> 生成给 Codex 使用的执行 Prompt
```

> 【插图位 3：loop-builder 工作流状态图】

最关键的一步，是先判断缺什么。

如果你没有上传目标图，`loop-builder` 应该停下来要图。目标图不是普通附件，它决定复杂度、最大轮次、差异评估方式和执行策略。

当目标图补齐后，它再输出任务卡和确认卡：

| 项目 | 推荐逻辑 |
|---|---|
| 场景 | UI 视觉复刻 / 截图对比 Loop |
| Loop 模式 | Plan-Execute-Verify |
| 反馈信号 | 目标图、当前截图、Top 差异清单 |
| 执行流程 | 目标图分析 -> 页面实现 -> 截图 -> 差异清单 -> 修 Top 3 -> 再截图 |
| 停止规则 | 达标、连续无改善、越界、目标图不可读、截图失败 |
| 人工确认 | 新依赖、业务逻辑调整、最终视觉验收 |

这张确认卡要先给人看。

你可以调整范围，比如只复刻桌面端、只改首页、不碰全局组件、最大轮次更保守。确认以后，`loop-builder` 才生成给 Codex 用的 Prompt。

Codex 负责进入项目执行；`loop-builder` 负责把执行方式设计清楚。

## loop-builder 生成的最小 Prompt

如果你确认了上面的工作逻辑，`loop-builder` 最后可以生成一段给 Codex 使用的执行 Prompt。

正文里放精简版，重点是让你看懂结构。真实使用时，再把目标图路径、项目入口和页面路由补进去。

```md
你现在是高级前端还原工程师，不是自由发挥的设计师。

任务：
根据目标 UI 视觉稿，高保真复刻当前页面。

输入：
- 目标视觉稿：<目标图路径或已附图>
- 当前页面入口：<URL / 路由 / 启动命令>
- 验收 viewport：优先 1440px 桌面宽度

工作流：
1. 先不要写代码，只做目标图分析和项目只读侦察。
2. 输出页面结构、组件树、颜色、字号、间距、圆角、阴影。
3. 制定分区实现计划。
4. 每轮实现后运行项目并截图。
5. 对比目标图和当前截图，列出 Top 5 视觉差异。
6. 每轮只修 Top 3 差异。
7. 达到停止条件后输出剩余差异和人工精修建议。

禁止动作：
- 不改业务逻辑、接口、权限、生产配置。
- 不引入新 UI 库，除非用户确认。
- 不自动提交，不自动发布。
- 不自行改变设计风格，不一次性大改。

停止规则：
- 我确认达标。
- 达到本次复杂度分析后的最大轮次。
- 连续 2 轮同类差异没有改善。
- 页面无法截图或目标图不可读。
```

这段 Prompt 已经比“照着图复刻页面”稳很多。

但它还不是长期资产。

如果你经常做这类任务，下一步才是 Skill 化。

## 跑通后再 Skill 化

如果你只做一次页面，保留 Prompt 就够了。

如果你经常遇到这些任务，就值得沉淀成专用 Skill：

| 固化内容 | 具体作用 |
|---|---|
| 角色定位 | 高级前端还原工程师，不自由发挥 |
| 输入契约 | 目标图、页面入口、技术栈、修改范围 |
| 执行节奏 | 分析、实现、截图、对比、修正 |
| 验收规则 | 目标图和当前截图对比，输出差异清单 |
| 停止规则 | 最大轮次、连续无改善、人工确认 |
| 禁止动作 | 不改业务逻辑，不自动提交，不自动发布 |

这也是我更看重 Loop Engineering 的地方：它把一次有效经验，沉淀成下一次可以复用的数字生产资料。

如果你也想试一次，可以按这张清单来：

| 步骤 | 动作 |
|---|---|
| 1 | 先选一个边界清楚的小页面，不要从复杂工作台开始 |
| 2 | 准备清晰目标图，来源可以是 imgGen、Figma 或产品截图 |
| 3 | 先让 Codex 做设计分析，不要直接写代码 |
| 4 | 每轮必须截图，不只看终端输出 |
| 5 | 每轮只修 Top 3 差异 |
| 6 | 最终视觉验收交给人 |
| 7 | 连续跑通两次以上，再沉淀成 Skill |

## 最后的判断

UI 复刻不是最复杂的编程任务，但它很能暴露 AI 编程的一个问题：

普通提示词擅长启动任务，却不擅长稳定收敛。

页面不像的时候，继续补一句“更像一点”，通常不够。

更可靠的做法，是把复刻过程拆成一个闭环：

```text
目标图
-> 当前页面
-> 截图
-> 差异清单
-> 修 Top 3
-> 再截图
-> 人工验收
```

这就是我这次用 `loop-builder` 处理 UI 复刻的核心原因。

它的目的不是把一个简单任务搞复杂。

真正要解决的，是把反复拉扯的修图式沟通，变成一条可验证、可停止、可复用的工作流。

如果你也有“AI 复刻 UI 总是不像”的案例，可以在评论区留言你的场景。

我会继续把这个 Visual Match Loop 整理成可复用 Skill 模板。
