# Loop 是什么、六块积木怎么搭？— 第2篇初稿

上一篇结尾我说：下一篇文章，我会系统拆解 Loop 的六块积木。

就是这篇。

如果你搭过 Loop，一定遇到过这些问题：

- Agent 跑了一次，下次再跑又从零开始——因为状态没存下来

- 两个 Agent 同时改一个文件，互相覆盖——因为没有隔离

- 每次 run 都要重新解释项目结构——因为知识没沉淀

- 只能读写本地文件，碰不到数据库和 issue tracker——因为没有连接器

这些不是 bug，是缺积木。

一个能真正转起来的 Loop，由六块积木构成。少一块，它就跑不顺。

今天逐个拆。

---

## 积木一：Automations —— 让 Loop 有心跳

没有心跳的 Loop 跑一次就死了。

Automations 是 recurring trigger——让 Loop 不需要你主动说"开始"，自己发现工作、自己启动。

**Claude Code 的实现方式：**

```
/loop "读取昨天 CI 失败和 open issues，
       写入 TODO.md，起草 quick-fix"
       --schedule "0 9 * * 1-5"
```

每周一到周五早上 9 点自动触发。你也可以用 Hooks——在 Agent 生命周期的关键点（启动前、完成后、出错时）自动触发 shell 命令。配合 GitHub Actions，即使你关了机，Loop 还在跑。

**Codex 的实现方式：**

Automations Tab——图形化配置：选项目、写 prompt、设 cadence、选 worktree。跑完后，有发现的 run 进入 Triage inbox，没发现的自动归档，不骚扰你。

**实操建议：**

起步用慢 cadence。每天一次就好。观察几天 token 消耗，再决定要不要加快。

> 一个常见错误：一上来就设每小时循环，然后被账单教育。

---

## 积木二：Worktrees —— 让 Agent 并行不碰撞

两个 Agent 写同一个文件 = 灾难。

想象一下：两个工程师 commit 到同一段代码，但不沟通。这就是没有 worktree 的多 Agent 场景。

**解决方案：git worktree**

每个 Agent 拿到独立工作目录 \+ 独立分支，但共享同一个 repo 历史。完成后自动清理，不残留。

- Codex 内置 worktree 支持

- Claude Code 通过 `--worktree` flag 和 `isolation: worktree` 设置

你可以这样并行：

```
主分支
├── worktree-A → Agent A 处理 auth 模块
├── worktree-B → Agent B 处理 billing 模块
└── worktree-C → Agent C 修复 CI 失败
```

**但有一个重要的警示：**

Worktree 消除了机械碰撞，没有消除审阅瓶颈。你能阅读和 approve 的速度，决定了实际能并行多少 Agent。

10 个 Agent 产出你无法 review 的变更，不如 2 个你能 fully review 的 Agent。

---

## 积木三：Skills —— 让知识不再每次从零开始

没有 Skills 的 Loop = 每次 run 从零重新推导项目。

每次 Agent 启动，如果都要重新理解"这个项目怎么构建、代码约定是什么、上次踩了什么坑"——你在浪费 token，也在浪费时间。

**Skills 的格式很简单：**

一个文件夹 \+ 一个 SKILL\.md 文件（指令 \+ 元数据）\+ 可选的 scripts / references / assets。

这里要区分两种东西：

- **Skill** = 持久项目知识（我们如何构建、约定是什么）——不太变

- **Memory** = 变化的状态（尝试了什么、什么通过了、什么还开放）——持续更新

**三条实操建议：**

1. 一个 Skill 对应一个任务。不要写一个巨大的"项目总览"，拆成"如何跑测试""如何部署""API 约定"等独立 Skill

2. 描述要 boring。SKILL\.md 的元数据是给 Agent 自动匹配用的，不是给人看的。越 boring 越容易被准确命中

3. 让 Agent 帮你整理。跑完一个项目后，让 Agent 自己把学到的约定和教训写成 Skill。它比你会总结

Skill 是 Loop Engineering 里最被低估的复利资产。你写下一个约定、示例、测试命令、永远不想重复的东西。随着时间增长，它是你项目里最值钱的 markdown 文件集合。

## 积木四：Plugins / Connectors —— 让 Loop 触达真实世界

只能看文件系统的 Loop，和能连接全工具链的 Loop，是两个物种。

基础协议：**Model Context Protocol（MCP）**

Codex 和 Claude Code 都支持 MCP。而且，为一个工具写的 connector 通常能在另一个工具中复用——这不是 vendor lock\-in 的游戏。

一个带 MCP 的 Loop 能做什么：

- 读取 Jira / Linear 里的 open issues

- 查询数据库验证数据迁移结果

- 调用 staging API 跑集成测试

- 往 Slack / 飞书发完成通知

没有 Connector 的 Loop 像一个被关在房间里的人——能思考，但碰不到外面的世界。

**实操：** 先接你最常用的那个工具。通常是 issue tracker 或 CI 系统。

---

## 积木五：Sub\-agents —— 让写代码的不判代码

单一模型有确认偏误——它会给自己打高分。

你让一个 Agent 写完代码，再让它自己检查——它大概率会说"没问题"。这不是故意骗你，是模型的天性。

**解法：分离"干活的"和"评判的"。**

这个思路来自 GAN（生成对抗网络）：Generator 生产 → Evaluator 评判 → 反馈 → Generator 迭代。同一个模型无法可靠评估自己的输出。单独训练一个 Evaluator 变得批判性，比让 Generator 自我批判容易得多。

**在 Loop 里的落地：**

- **Maker sub\-agent**：负责起草代码

- **Checker sub\-agent**：对照测试、spec、linter 进行验证

Claude Code 的 /goal 就是这样工作的：代码生成委托给 helper sub\-agents，独立的 evaluator model 持续验证停止条件——空 linter log、单元测试通过，才算 done。

**这条原则记住：验证模型比生成模型更省钱。** 因为验证器跑的轮次少、判断快。

---

## 积木六：Memory —— 让 Loop 记得昨天做了什么

模型会遗忘，但 repo 不会。

Memory 的形式可以是 markdown 文件、Linear board、GitHub issue list。唯一要求：**活在 context window 之外。**

它的作用很简单：明天的 run 读取 state file，从今天停下的地方继续。

一个典型的 state file 长这样：

```Markdown
## 目标
- [ ] 所有 test/auth 测试通过
- [ ] Lint 无错误

## 状态
- [x] 已修复 test/auth/login.test.ts
- [ ] 待处理 test/auth/token.test.ts

## 日志
| 时间 | 动作 | 结果 | 下一步 |
|------|------|------|--------|
| 09:00 | 修复 login | ✅ 通过 | 处理 token |
```

没有 Memory 的 Loop 像一个每天失忆的工人——每天早上重新问"我今天该干什么"。

## 六块积木怎么搭：从零到第一个 Loop

知道积木是什么之后，怎么把它们搭起来？

**第一步：准备项目基础（Skills \+ Memory）**

先写 CLAUDE\.md 或 AGENTS\.md，包含：

- 项目构建步骤

- 测试命令

- 代码约定（"我们不这样做，因为那次事故"）

- 术语表

同时创建第一个 state file（TODO\.md 或 loop\-state\.md），定义你要让 Loop 完成的目标。

**第二步：定义可验证目标**

好目标：`"test/auth 中所有测试通过且 lint 干净"`
坏目标：`"让 app 更好"`

标准只有三条：

- 足够具体以评估

- 可拆分为可测试子任务

- 范围不超出 Agent 能力

**第三步：配置调度器和断路器**

用 /loop 或 Automations 设一个慢 cadence（比如每天早晨 9 点）。

然后必须设断路器：

- `max_consecutive_failures` — 连续失败上限

- `max_runtime_min` — 硬时钟超时

- Token / Dollar 预算 — 每日上限

- No\-progress 检测 — 停滞自动停止

> 没有断路器的 Loop 是一辆没刹车的车。

**第四步：加上 Worktree 和 Sub\-agents**

每次 run 在独立 worktree 里执行。如果任务够大，拆成 Maker \+ Checker 两个 sub\-agent。

**第五步：接上 Connector**

如果你用 Linear 管 issue，接一个 MCP connector 让 Loop 能读取 open tickets。如果你用飞书协作，让 Loop 完成后往群里发通知。

**完整的 Loop 就跑起来了：**

```
每天 9:00 自动触发（Automations）
    ↓
读取 CI 失败 + open issues（Connector）
    ↓
写入 state file（Memory）
    ↓
在独立 worktree 中打开一个 issue（Worktree）
    ↓
Maker Agent 起草修复（Sub-agent）
    ↓
Checker Agent 验证（Sub-agent）
    ↓
通过 → 开 PR + 更新 ticket
失败 → 反馈 1-2 次
卡住 → 停止 + 放入收件箱
```

**第五步之后：持续沉淀 Skills**

每次 Loop 跑完，让它把学到的约定和模式写成 Skill。下一次 run 就能直接读取，不再从零开始。

这就是复利。

## 成本管控：三条铁律

Loop 能烧钱，也能省钱。区别在于你怎么控。

1. 启动慢 cadence \+ 紧 goal 条件。先跑几天看 cost，再决定要不要加速

2. 验证模型比生成模型便宜。用轻量模型做 checker，重模型只在需要时调用

3. 硬制动必须设。迭代次数上限 \+ 无进展检测 \+ 预算上限——三条全设

> 预算本身就是 Loop 架构的一部分，不是事后优化项。
