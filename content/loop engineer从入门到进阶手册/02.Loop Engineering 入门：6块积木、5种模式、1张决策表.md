# Loop Engineering 入门：6 块积木、5 种模式、1 张决策表

> Loop Engineering 系列 · 第二篇

> 上一篇讲了为什么工程师的工作正在从“写提示词”变成“写循环”。这一篇不急着上工具，先把地图摊开：你手里有哪些积木，常见任务该用哪种 Loop，最后用一张表做选择。

---

同样是让 Agent 干活，修一个 lint 错误、重构认证模块、排查线上 500、修改支付流程、长期维护一个项目，不能用同一种循环。

修 lint 错误时，你需要的是快速执行、快速验证、失败就改。

重构模块时，你需要先理解结构，再列计划，再一小步一小步验证。

排查线上 500 时，你一开始根本不知道问题在哪，需要并行探索几条线索。

修改支付流程时，Agent 不能自己一路改到底，关键节点必须停下来等人确认。

长期做一个项目时，你还要把经验沉淀下来，让下一轮不再从零开始。

这就是第二篇要解决的问题：

**Loop 的积木有哪些？任务不同，应该选哪种 Loop？**

先说结论。

Loop Engineering 可以先按这个结构理解：

```text
6 块积木：你有什么能力
5 种模式：你怎么组合能力
1 张决策表：当前任务该选哪种模式
```

你不需要一上来就搭一个复杂系统。大多数人真正需要的，是先知道自己正在处理哪类任务，再选一个足够轻的循环。

---

## 01 六块积木：一个 Loop 靠什么跑起来

一个 Loop 能跑起来，不只靠一句 prompt。

它至少需要六块积木。

### 1. Automations：让循环转起来

Automations 是心跳。

它负责让任务在某个时间、某个事件、某个条件下再次启动。

比如：

- 每 10 分钟检查一次部署状态。
- 每天早上生成项目状态摘要。
- PR 有新评论时触发处理。
- CI 失败后启动修复流程。

Automations 解决的是“什么时候再来一轮”。

但它本身不保证结果正确。

一个自动运行的坏流程，只会更稳定地制造坏结果。所以 Automations 必须和反馈、停止规则、权限控制一起用。

### 2. Worktrees：让多个尝试互不污染

Worktrees 解决并行和隔离问题。

你可以让不同 Agent 在不同分支或工作区里尝试不同方案。

一个 Agent 修登录 bug。

一个 Agent 查性能瓶颈。

一个 Agent 改测试。

它们互不影响，最后再由人或 Evaluator 判断哪条路径值得合并。

Worktrees 特别适合探索型任务。

如果你还不知道正确方向，让多个尝试隔离运行，比让一个 Agent 在同一个目录里来回改更稳。

### 3. Skills：把经验沉淀下来

Skills 是可复用知识。

每次你告诉 Agent：

- 这个项目怎么跑测试。
- 哪些文件不能动。
- 代码风格是什么。
- Review 时重点看什么。
- 发布前要检查哪些项。

这些都不应该每次重新解释。

它们应该沉淀成 Skill、规则、模板或项目说明。

Skills 解决的是“下一次别再从零开始”。

一个好的 Loop 跑完之后，除了产出代码或文档，还应该留下可复用经验。

### 4. Connectors / MCP：让 Agent 接触真实世界

Loop 如果只在聊天窗口里自言自语，价值有限。

它需要接触真实工具链：

- GitHub / GitLab。
- 浏览器。
- 文档系统。
- 数据库。
- CI。
- 日志。
- 项目管理工具。

Connectors 或 MCP 的作用，是让 Agent 能读真实状态、调用真实工具、拿到真实反馈。

这块能力很强，也最容易带来风险。

一旦 Agent 能操作真实系统，你就必须设置权限边界：什么能自动做，什么必须审批，什么永远禁止。

### 5. Maker / Checker：写的和判的分开

Maker 负责生成。

Checker 负责判断。

这是 Loop 里最容易被低估的一块。

很多人让同一个 Agent 写代码，再让它自己检查。结果往往是：它会沿着自己刚才的思路证明自己没错。

真正可靠的 Loop，要把“产出”和“验收”分开。

在代码场景里：

- Maker 写 patch。
- Checker 看 diff、跑测试、查边界情况。

在内容场景里：

- Maker 写草稿。
- Checker 查来源、反向证据、读者获得感、平台适配。

Maker / Checker 分工，是后面三角色架构的基础。

### 6. Memory：让状态留在模型外面

模型会忘。

上下文会压缩。

会话会结束。

所以重要状态不能只放在模型脑子里。

Memory 可以是文件、日志、数据库、任务板、source pack、review 记录，也可以是项目里的 `AGENTS.md`、`CLAUDE.md`、`SKILL.md`。

它解决的是“下一轮从哪里接着做”。

一个 Loop 如果没有外部 Memory，每一轮都像新来的实习生。它可能很聪明，但一直缺历史。

## 02 五种模式：不同任务用不同循环

有了六块积木，下一步不是全部装上。

下一步是判断任务类型。

常见的 Loop 可以先分成五种模式。

### 模式一：Retry Loop

最轻的循环。

逻辑很简单：

```text
执行 -> 验证 -> 失败则重试 -> 通过则停止
```

适合：

- 修 lint。
- 修一个已知测试失败。
- 写一个小函数。
- 跑通一个明确接口。

例子：

```text
修复当前失败的 email validator 测试。
每次修改后运行对应测试。
最多重试 3 次。
如果同一个测试连续失败 2 次，停止并说明原因。
```

Retry Loop 的关键，是必须有明确 pass / fail。

没有验证标准时，重试只会变成反复猜。

适合它的任务通常短、窄、可测试。

### 模式二：Plan-Execute-Verify Loop

比 Retry 多一个规划阶段。

逻辑是：

```text
先计划 -> 再执行 -> 再验证 -> 失败后修订计划
```

适合：

- 重构一个模块。
- 搭建一个新服务。
- 做数据库迁移。
- 改一段影响面比较大的业务逻辑。

例子：

```text
重构 authentication 模块。
先列出涉及文件和修改顺序。
不要直接改代码。
计划确认后逐步执行。
每完成一步运行对应测试。
如果测试失败，先修订计划，再继续。
```

这个模式的重点是“先别动手”。

很多 Agent 翻车，根源常常在第一步方向就错了。

多步骤任务里，早期错误会级联。先规划能减少后面反复返工。

### 模式三：Explore-Narrow Loop

当你不知道问题在哪时，用探索-收窄。

逻辑是：

```text
并行探索几条路径 -> 根据证据剪枝 -> 聚焦最可能方向 -> 深入处理
```

适合：

- 间歇性 500 错误。
- 性能瓶颈排查。
- 不熟悉 API 的调用方式探索。
- 技术选型。

例子：

```text
接口偶发 500。
请并行检查三条线索：
1. 数据库连接池是否耗尽。
2. 上游服务是否限流。
3. 请求处理是否存在内存泄漏。
每条线索只做前两步证据检查。
没有证据就剪枝。
最后给出最可能原因和下一步验证计划。
```

Explore-Narrow 的风险是上下文爆炸。

如果每条线索都不舍得放弃，Agent 很快会背着一堆未证实的猜测继续跑。

这个模式必须早剪枝。

### 模式四：Human-in-the-Loop

人在关键节点进入循环。

逻辑是：

```text
Agent 执行低风险步骤 -> 遇到高代价决策 -> 停下来等人 -> 人确认后继续
```

适合：

- 生产环境变更。
- 支付、权限、用户数据相关修改。
- 产品方向选择。
- 无法完全提前写清楚的需求。

例子：

```text
重构支付模块。
日志、测试、注释可以自动修改。
任何影响 charge flow 的改动，都必须先展示 proposed diff，等我确认后再继续。
禁止直接修改生产配置。
```

Human-in-the-Loop 的关键不是“每一步都问人”。

那样会把人拖回人肉中转站。

正确做法是把审批粒度放在影响面上：低风险自动走，高风险停下来。

### 模式五：Lifecycle Loop

最重的一种。

它面向长期项目，不适合用来处理单次小任务。

你可以把它理解成：

```text
规划 -> 迭代 -> 验证 -> 沉淀 -> 下一轮规划
```

适合：

- 从 0 到 1 做一个功能。
- 长期维护一个项目。
- 持续改进一个内容系统。
- 希望 Skill、模板、规则越用越厚。

它通常会把前面四种模式嵌进去：

```text
规划阶段：产出本轮目标和验收标准
迭代阶段：子任务用 Retry / Plan-Execute-Verify / Explore-Narrow
验证阶段：Checker 或 Evaluator 独立验收
沉淀阶段：把经验写回 Skill、Memory、项目文档
```

Lifecycle Loop 的风险是太重。

修一个 typo 不需要生命周期管理。

它适合值得长期投入的项目。

如果一个任务只做一次，用轻量模式就够了。

## 03 一张决策表：当前任务怎么选

先看任务性格，再选 Loop。

|任务特征|推荐模式|核心判断|
|---|---|---|
|目标明确，有清晰 pass / fail|Retry Loop|最小闭环，先执行再验证|
|步骤多，有顺序依赖|Plan-Execute-Verify|先规划，避免早期错误级联|
|原因未知，需要排查|Explore-Narrow|先并行探索，再快速剪枝|
|涉及高代价决策|Human-in-the-Loop|低风险自动走，高风险交还给人|
|长期项目，需要知识沉淀|Lifecycle Loop|规划、迭代、验证、沉淀循环推进|

再换成判断流程：

```text
任务有清晰 pass / fail 吗？
├── 有 → Retry Loop
└── 没有 → 任务是否多步骤、有依赖？
    ├── 是 → Plan-Execute-Verify
    └── 否 → 是否需要探索未知原因？
        ├── 是 → Explore-Narrow
        └── 否 → 是否涉及高代价决策？
            ├── 是 → Human-in-the-Loop
            └── 否 → 先人工澄清目标

项目是否值得长期沉淀？
├── 值得 → 外层套 Lifecycle Loop
└── 不值得 → 保持轻量模式
```

这张表还有一个隐含原则：

**能用轻量 Loop，就不要上重型 Loop。**

Loop Engineering 不是自动化越多越高级。

好系统的标准，是任务刚好被放进合适的循环里。

## 04 一个完整例子：线上接口偶发 500

假设你遇到一个线上接口偶发 500。

不要一上来就说：

```text
帮我修一下这个 bug。
```

这句话会让 Agent 在没有边界的情况下开始猜。

更好的做法是先判断任务类型。

这个任务有清晰 pass / fail 吗？

暂时没有。因为你还不知道根因。

它需要探索吗？

需要。

所以第一层应该用 Explore-Narrow：

```text
接口偶发 500。
先并行检查三条线索：
1. 数据库连接池。
2. 上游限流。
3. 请求处理异常。
每条线索只查日志和指标，不改代码。
没有证据就剪枝。
```

假设最后发现是数据库连接池耗尽。

此时任务从“探索”变成“修复”。

如果修复很小，比如调整连接池配置和超时处理，可以切到 Plan-Execute-Verify：

```text
先列出需要修改的配置、代码和测试。
确认修改顺序。
每完成一步运行对应测试。
如果测试失败，先修订计划。
```

如果涉及生产数据库配置，则必须加入 Human-in-the-Loop：

```text
任何生产配置变更都只生成方案，不直接执行。
列出风险、回滚方式和验证步骤，等待人工确认。
```

如果这个服务长期要维护，还要把经验写回 Memory：

```text
把本次故障的根因、排查路径、验证命令、回滚方案写入 incident note。
后续遇到类似 500，优先检查连接池指标。
```

这就是 Loop 的组合。

你不是在找一个万能模式。

你是在根据任务状态切换模式。

## 05 第一次搭 Loop，从哪里开始

第一次不要上 Lifecycle Loop。

也不要急着搞一堆 Agent 并行。

先选一个最小任务：

- 一个确定失败的测试。
- 一个 lint 错误。
- 一个小函数。
- 一个固定格式的周报整理。
- 一个资料来源检查。

然后只写四条规则：

```text
目标：这一轮要完成什么。
反馈：用什么判断完成。
停止：什么时候结束。
拒绝：哪些动作禁止。
```

例如：

```text
修复当前失败的单元测试。
每次修改后只运行这个测试文件。
最多尝试 3 轮。
如果同一个错误连续出现 2 次，停止并说明卡点。
禁止修改无关文件。
```

跑通一次，你会立刻理解三件事：

- 为什么 pass / fail 是 Loop 的地基。
- 为什么无限重试会浪费时间。
- 为什么人必须提前写清停止和拒绝规则。

Loop Engineering 是跑出来的。

先跑一个最小闭环，再加 Automations、Worktrees、Skills、Connectors、Maker/Checker、Memory。

顺序反了，就会变成用复杂工具包装一个模糊目标。

## 06 下一篇：Agent 写出来的东西，谁来审？

这篇解决了两个问题：

- 你手里有哪些积木。
- 当前任务该选哪种 Loop 模式。

但还有一个更关键的问题没解决：

**Agent 写出来的东西，谁来审？**

如果让同一个 Agent 既写代码又判断代码，它很容易沿着自己的思路证明自己没错。

下一篇讲三角色架构：

- Planner：把需求拆成可执行计划。
- Generator：按计划生成产物。
- Evaluator：独立验证产物是否达标。

当 Evaluator 真正独立出来，Loop 才开始接近工程闭环。
