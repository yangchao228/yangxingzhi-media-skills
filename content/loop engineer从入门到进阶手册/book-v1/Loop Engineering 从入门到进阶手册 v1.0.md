## 前言：为什么要写这本手册

过去一段时间，很多人学习 AI 编程的方式，是不断优化提示词。

提示词当然重要。一个清楚的任务描述、完整的上下文、明确的验收标准，能显著提高 Agent 的输出质量。但当任务从“一次性回答”进入“持续做事”，提示词很快就会到达边界。

你会遇到这些问题：

- 每次都要重新解释项目背景。
- Agent 修完一个问题，又忘了上一轮为什么这么改。
- 任务跑偏后，没有明确的停止规则。
- 结果看起来通过了，但没有独立验收。
- 成本越跑越高，人却不知道哪里失控。

这时，问题已经不只是提示词写得好不好。

你需要设计一个系统：它有目标，有状态，有反馈，有执行者，有验收者，也有停止条件。

这就是本书讨论的 Loop Engineering。

Loop Engineering 的价值，不是让 AI 替人做所有决定。它的价值在于，把重复任务、工具调用、反馈机制和判断边界组织成可复用的循环系统。

从这个角度看，人的角色也在变化。

过去你可能是提示词作者。现在你更像系统设计者：你定义目标，设计反馈，设置边界，保留最终判断权，再让 Agent 在安全范围内持续执行。

本书基于一个公众号系列整理而来，但它不会按文章顺序简单合订。公众号适合一篇篇讲清楚，手册需要重新组织：先建立概念，再拆结构，接着讲模式和角色，最后落到 Codex CI 自动修复实战。

读完这本书，你至少应该能完成三件事：

- 判断一个任务是否适合做成 Loop。
- 设计一个可验证、可停止、可纠错的最小 Loop。
- 用模板搭建第一个 Codex CI 修复 Loop，并知道它的风险边界。

# 第一部分：为什么需要 Loop Engineering

## 第 1 章：从提示词到循环系统

AI 编程的第一阶段，是提示词。

你告诉模型：“帮我写一个函数”“帮我修这个 bug”“帮我解释这段代码”。模型给出结果，你检查，满意就用，不满意就继续追问。

这个阶段的问题很清楚：效率提高了，但人还是每一轮的调度器。

你要不断补上下文、解释约束、检查结果、指出问题。Agent 像一个很强的执行者，但每一步都要你推一下。

后来大家开始重视 Context。

Context 解决的问题是：模型不能只看一句话，它需要项目结构、接口约定、测试命令、代码风格、业务限制。于是我们开始写 `AGENTS.md`、`CLAUDE.md`、项目规则、代码规范，把上下文变成可复用资产。

再往后是 Harness。

Harness 可以理解为“把模型装进一个工程外壳”。它负责把工具、上下文、任务队列、权限、评估标准组织起来。此时人不再只写一句提示词，而是在设计模型和工具之间的协作规则。

Loop 是下一步。

Loop 让系统开始周期性运行：它读取状态，选择任务，调用 Agent，执行验证，写回结果，根据反馈决定继续、停止、回滚或交给人。

四层演进可以这样看：

| 层级 | 人主要做什么 | 系统主要解决什么 |
|---|---|---|
| Prompt | 写清单轮任务 | 让模型完成一次回答 |
| Context | 提供项目背景 | 减少每轮重复解释 |
| Harness | 组织工具和规则 | 让模型能调用真实环境 |
| Loop | 设计反馈闭环 | 让系统能持续做事并受控停止 |

这四层不是互斥关系。一个好的 Loop 仍然需要清楚的 Prompt，也需要稳定的 Context，还需要 Harness 承载工具和规则。

关键变化在于：人的工作重心上移了。

你不再只问“这句话怎么写得更好”，还要问：

- 这个任务是否值得循环？
- 每一轮怎么判断成功？
- 哪些状态必须写在模型外？
- 谁来生成，谁来验收？
- 失败几次必须停？
- 哪些动作永远需要人确认？

这就是 Loop Engineering 的起点。

### 本章行动清单

- 找一个你反复让 AI 做的任务。
- 写出它当前依赖你手动调度的步骤。
- 标出哪些步骤可以自动执行，哪些步骤必须人工确认。
- 判断它现在处于 Prompt、Context、Harness、Loop 哪一层。

## 第 2 章：Loop 到底是什么

一个 Loop 不是简单重复。

如果你只是每小时让 Agent 运行同一句提示词，那更像定时任务。它可能能省一点手工操作，但它没有真正的反馈闭环。

一个可控 Loop 至少包含六个要素：

| 要素 | 作用 | 缺失后的问题 |
|---|---|---|
| 目标 | 定义要解决什么 | Agent 容易发散 |
| 状态 | 记录当前进展 | 每轮都像冷启动 |
| 执行 | 让 Agent 处理任务 | 只有计划，没有产出 |
| 反馈 | 用测试、日志、diff 等验证 | Agent 容易自我确认 |
| 停止规则 | 决定何时停下 | 循环失控、成本失控 |
| 人工边界 | 明确哪些动作交给人 | 自动化越权 |

Loop Engineering 的核心，是让 Agent 在有边界的系统里循环，而不是单纯拉长运行时间。

可以用三条标准判断一个 Loop 是否合格。

第一，是否可验证。

一个 Loop 必须有外部信号。代码任务可以看测试、lint、type check、CI 日志、diff。内容任务可以看结构清单、事实来源、标题承诺、平台适配度。没有外部信号，Agent 很容易把“看起来合理”当成“已经完成”。

第二，是否可停止。

循环必须知道什么时候停。连续失败几次停？运行多久停？遇到高风险文件停？缺少权限停？成本超过阈值停？这些规则要提前写清楚。

第三，是否可纠错。

一个 Loop 不该只记录成功，也要记录失败。失败报告至少包括：试过什么、为什么失败、下一步需要谁判断。这样人接手时不需要重新排查。

和常见概念对比：

| 概念 | 重点 | 局限 |
|---|---|---|
| Prompt | 单次任务描述 | 依赖人手动调度 |
| Workflow | 固定流程编排 | 不一定有智能判断 |
| Agent | 能调用工具的模型 | 容易缺反馈和边界 |
| Cron Job | 按时间触发 | 不理解任务状态 |
| Loop | 状态 + 反馈 + 停止规则 | 需要工程设计和成本控制 |

最小 Loop 可以很小。

例如：

1. 每天检查一次失败测试。
2. 从失败日志里选一个范围小的问题。
3. 让 Maker 做最小修复。
4. 让 Checker 独立验收。
5. 测试通过就留下 PR 摘要。
6. 连续失败两次就停止并交给人。

这已经是一个 Loop。

它不复杂，但它有目标、状态、执行、反馈、停止规则和人工边界。

### 本章行动清单

- 给你的任务写一句明确目标。
- 写出一个外部验收信号。
- 写出一个停止条件。
- 写出一个必须交给人确认的动作。

# 第二部分：Loop 的结构和模式

## 第 3 章：六块积木：一个 Loop 靠什么跑起来

一个 Loop 能跑起来，通常需要六块积木。

它们不是同一层级。有的是基础设施，有的是协作约束，有的是状态系统。

| 积木 | 层级 | 作用 |
|---|---|---|
| Automations | 触发层 | 让 Loop 按时间或事件启动 |
| Worktrees | 隔离层 | 让多个尝试互不污染 |
| Skills | 知识层 | 把经验写成可复用规则 |
| Connectors | 工具层 | 连接真实系统和数据 |
| Sub-agents | 协作层 | 拆分生成和验证角色 |
| Memory | 状态层 | 把进展写在模型外面 |

### Automations：让 Loop 有心跳

Automations 解决触发问题。

触发可以是时间，也可以是事件。时间触发常见于每日检查、每周复盘、定期扫描。事件触发常见于 CI 失败、PR 更新、issue 新增、监控告警。

新手最容易犯的错误，是一开始就把间隔设得很短。第一个 Loop 每天跑一次就够了。先看候选任务质量，再决定是否提高频率。

### Worktrees：让多个尝试互不污染

当 Agent 开始改代码，隔离就很重要。

一个 Loop 可能会尝试不同修复路径。如果都在同一个工作区里做，很容易出现脏 diff、互相覆盖、回滚困难。

Git branch、Git worktree、临时目录，都是隔离手段。工具选择服务于同一个目标：保证每次尝试可以独立检查、独立丢弃、独立合并。

### Skills：让知识不再每次从零开始

如果你每次都要告诉 Agent“怎么跑测试、哪些文件不能碰、怎么写 PR 摘要”，那说明经验还没有沉淀。

Skills 的作用，是把这些经验写成可复用规则。

在一个项目里，最小 Skill 可以很朴素：

- 安装命令。
- 测试命令。
- 代码风格。
- 禁止修改的目录。
- 高风险操作清单。
- PR 摘要格式。

### Connectors：让 Loop 接触真实工具链

Loop 需要真实反馈，很多反馈来自外部系统。

例如：

- GitHub / GitLab 提供 PR、CI、issue。
- 数据库提供真实状态。
- 日志平台提供错误信号。
- 邮件、Slack、飞书提供通知入口。

Connector 的风险也很清楚：连接越多，权限越要谨慎。第一个 Loop 尽量只读。先让它读日志、读失败信息、读 diff，再逐步开放写权限。

### Sub-agents：让生成和验证分开

如果同一个 Agent 既负责修改，又负责宣布自己修改成功，风险会很高。

最小拆法是 Maker + Checker。

Maker 负责最小修复。Checker 负责只读验收。

这个拆分会增加一点成本，但能显著降低自我确认风险。

### Memory：让 Loop 记得昨天做到哪里

聊天上下文不适合当唯一记忆。

上下文会截断，会丢失，也很难被人审阅。更稳的方式，是把状态写到模型外面，例如 `TODO.md`、issue、数据库、任务表。

一个最小状态文件至少记录：

- 当前目标。
- 候选问题。
- 当前尝试。
- 最近命令。
- 最近结果。
- 下一步。
- 运行日志。

### 六块积木的最小装配顺序

第一次搭 Loop，不需要一次配齐所有高级能力。

推荐顺序：

1. 写清项目规则。
2. 定义可验证目标。
3. 建立状态文件。
4. 先只读侦察。
5. 再开放最小写权限。
6. 引入 Checker。
7. 最后加定时调度。

### 本章行动清单

- 给你的项目补一份 `AGENTS.md`。
- 写一个 `TODO.md` 状态文件。
- 找到一个真实反馈源：测试、日志、CI 或 diff。
- 明确第一个 Loop 暂时只读，还是允许最小写入。

## 第 4 章：五种 Loop 模式：不同任务怎么选

Loop 不是一种固定形态。

不同任务适合不同循环。选错模式，比不用 Loop 更浪费时间。

### 模式一：Retry Loop

适合目标明确、失败信号清楚、修复范围小的任务。

例如：

- 一个测试失败。
- 一个 lint 报错。
- 一个格式校验失败。

基本结构：

```text
执行 -> 验证 -> 失败则最小修复 -> 再验证 -> 达到上限后停止
```

适合：

- 有确定 pass/fail 信号。
- 修改范围很小。
- 失败原因大概率在局部文件。

不适合：

- 原因未知的线上故障。
- 涉及产品判断的需求。
- 影响范围很大的重构。

### 模式二：Plan-Execute-Verify

适合步骤复杂，但目标可以分解的任务。

例如：

- 增加一个小功能。
- 改造一个接口。
- 拆分一个模块。

基本结构：

```text
规划 -> 执行 -> 验证 -> 回写状态 -> 继续下一步
```

这个模式的重点是 Planner。Planner 要把一句话需求拆成可执行 checklist，并明确每一步的验收方式。

### 模式三：Explore-Narrow

适合原因未知的问题。

例如：

- 线上接口偶发 500。
- 某个耗时突然增加。
- 一个 bug 复现条件不稳定。

基本结构：

```text
广泛侦察 -> 收窄假设 -> 验证假设 -> 输出下一步
```

这个模式前期应该偏只读。先查日志、代码路径、配置、最近变更，不要急着改。

### 模式四：Human-in-the-Loop

适合高风险任务。

例如：

- 权限系统。
- 支付流程。
- 数据删除。
- 生产配置。
- 自动 merge。

基本结构：

```text
Agent 准备方案 -> 人确认 -> Agent 执行受限步骤 -> 人验收
```

这里的关键，是明确哪些节点必须由人判断。

### 模式五：Lifecycle Loop

适合长期项目维护。

例如：

- 每日扫描失败 CI。
- 每周清理依赖风险。
- 持续整理 issue。
- 定期生成健康报告。

基本结构：

```text
扫描 -> 排序 -> 处理 -> 验收 -> 记录 -> 下次继续
```

Lifecycle Loop 的关键是状态。它必须知道上次做了什么，这次该接着哪里做。

### 决策表

| 任务特征 | 推荐模式 |
|---|---|
| 目标明确，反馈清楚 | Retry Loop |
| 步骤多，需要拆解 | Plan-Execute-Verify |
| 原因未知，需要排查 | Explore-Narrow |
| 风险高，需要人判断 | Human-in-the-Loop |
| 长期维护，周期运行 | Lifecycle Loop |

- 选一个你想自动化的任务。
- 判断它属于哪一种模式。
- 写出它的反馈信号。
- 写出它的停止规则。
- 写出它需要人工确认的节点。

## 第 5 章：三角色闭环：谁规划、谁生成、谁验收

很多 Agent 任务失败，并不是因为模型完全不会做。

更常见的问题是：同一个 Agent 既规划、又实现、又给自己打分。

这会放大两个问题。

第一，上下文焦虑。

Agent 拿到大量信息后，容易为了“看起来完整”而扩大范围。它会开始解释很多背景，改很多文件，最后偏离最初目标。

第二，自我评估偏误。

生成者天然倾向于相信自己的结果。让它自己宣布“我已经完成”，风险很高。

一个更稳的结构，是三角色闭环。

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| Planner | 拆目标、定约束、写验收标准 | 不直接实现 |
| Generator / Maker | 按计划生成或修改 | 不宣布最终通过 |
| Evaluator / Checker | 独立验证、指出风险 | 不改代码 |

### Planner：把需求变成可执行 spec

Planner 的价值，是把模糊需求变成可执行计划。

一个好的 Planner 输出至少包含：

- 目标。
- 范围。
- 非目标。
- 验收标准。
- 风险点。
- 需要人工确认的节点。

### Generator / Maker：专注最小实现

Maker 的任务是做最小改动。

它不应该顺手重构，不应该扩大范围，不应该修改测试预期来适配错误实现。

Maker prompt 里要反复强调：

- 只处理当前任务。
- 只改相关文件。
- 修改后运行指定验证命令。
- 失败要记录，不要硬撑。

### Evaluator / Checker：独立验收

Checker 的职责，是保护代码库和工作流。

它应该只读。它看 diff、看测试、看状态文件、看风险。它不负责鼓励 Maker，也不负责替 Maker 圆场。

Checker 至少检查：

- 是否只改相关文件。
- 是否存在无关重构。
- 是否修改测试预期。
- 验证命令是否真实运行。
- 结果是否真的通过。
- 是否引入权限、密钥、生产配置风险。

### Harness：让三角色按规则协作

Harness 是三角色之间的工程外壳。

它可以很复杂，也可以很简单。最小 Harness 可以只是：

- 一个 `AGENTS.md`。
- 一个 `TODO.md`。
- 一组 Maker / Checker prompt。
- 一套测试命令。
- 一条停止规则。

不要把 Harness 神秘化。它的核心作用，是把角色、工具、状态和规则组织起来。

### 本章行动清单

- 把你常用的一个 Prompt 拆成 Planner / Maker / Checker。
- 为 Checker 写一组只读检查项。
- 规定 Maker 不允许做的三件事。
- 把验收标准写成 checklist。

# 第三部分：从 0 到 1 搭建第一个 Loop

## 第 6 章：Codex 实战：从零搭建 CI 自动修复 Loop

第一个 Loop 不要选太大的目标。

不要从“自动维护整个项目”开始。更稳的选择，是 CI 自动修复。

原因很简单：

- CI 有明确失败信号。
- 测试可以作为外部反馈。
- diff 可以被人 review。
- 高风险动作可以先排除。
- 失败也能留下报告。

本章的目标，是搭一个最小可跑的 Codex CI 修复 Loop。

它做这些事：

1. 检查失败测试或明确 bug。
2. 选择一个可验证的小问题。
3. 生成最小修复。
4. 运行测试。
5. 写回状态。
6. 由 Checker 验收。
7. 留下可 review 的 diff 和 PR 摘要。

它暂时不做这些事：

- 不自动 merge。
- 不改生产配置。
- 不处理支付、权限、数据删除。
- 不做大重构。
- 不替人做最终判断。

### 前置条件

项目至少满足五个条件。

| 条件 | 检查方式 |
|---|---|
| 有测试 | `npm test`、`pytest`、`python3 -m unittest` 等 |
| 是 Git 仓库 | `git status` |
| 有干净基线提交 | `git log --oneline -1` |
| 有项目规则 | `AGENTS.md` |
| Codex CLI 能运行 | `codex exec --sandbox read-only "只读取 AGENTS.md"` |

刚建的小项目，要先提交一次 baseline。否则 Checker 看 diff 时，会把所有文件都当成本轮改动。

### 状态文件

第一个状态文件可以叫 `TODO.md`。

它要记录目标、候选问题、当前尝试和运行日志。

最小结构：

```markdown
# TODO.md - CI 修复 Loop 状态

## Goal
- [ ] 修复一个有明确失败信号的 CI 问题
- [ ] 相关测试通过
- [ ] 不做无关重构
- [ ] 如果失败，记录尝试过程和阻塞原因

## Candidate Issues
| 优先级 | 来源 | 失败信号 | 处理状态 |
|---|---|---|---|
| P1 | CI log | test/auth/login.test.ts failed | 待处理 |

## Current Attempt
- Issue:
- Branch:
- Last command:
- Last result:
- Next action:

## Log
| 时间 | 动作 | 结果 | 下一步 |
|---|---|---|---|
| | | | |
```

### 第一步：只读侦察

先不要让 Agent 改代码。

只读侦察的目标是筛选问题。

```bash
codex exec --sandbox read-only \
  "阅读 AGENTS.md、TODO.md 和最近的测试输出。
   找出一个最适合自动修复的问题。
   只允许输出分析，不要修改文件。
   输出内容包括：
   1. 失败信号
   2. 相关文件
   3. 推荐修复范围
   4. 验收命令
   5. 是否适合进入自动修复 Loop"
```

### 第二步：Maker 最小修复

侦察通过后，再让 Maker 处理。

Maker prompt 的关键是限制范围。

```bash
codex exec --sandbox workspace-write \
  "你是 Maker。
   读取 AGENTS.md 和 TODO.md。
   只处理 TODO.md 中优先级最高、且有明确失败信号的问题。
   要求：
   1. 先说明你准备修改哪些文件
   2. 只做最小修复，不做无关重构
   3. 修改后运行 TODO.md 中的验收命令
   4. 把运行结果写回 TODO.md
   5. 如果连续 2 次同一测试失败，停止并记录阻塞原因
   6. 不要 push，不要 merge，不要修改生产配置"
```

### 第三步：Checker 独立验收

Maker 完成后，不要让 Maker 自己宣布成功。

```bash
codex exec --sandbox read-only \
  "你是 Checker。
   请审核当前 diff 和 TODO.md。
   只做验证，不要修改代码。
   检查项：
   1. 是否只修改了相关文件
   2. 是否存在无关重构
   3. 是否运行了约定测试
   4. 测试结果是否真的通过
   5. 是否引入安全风险、硬编码密钥或危险权限
   6. 如果不通过，请列出具体失败原因和下一步建议
   7. 如果通过，请生成 PR 摘要"
```

### 本地烟测发现的问题

在一个只有 4 个文件的本地临时项目里，这条链路可以跑通。

测试项目的失败信号是：登录失败时返回 `500`，测试期望 `401`。Maker 只改了一行代码，Checker 确认没有修改测试，也没有无关重构。

但烟测也暴露了几个真实问题：

- 没有基线提交时，diff 很脏。
- `codex exec` 可能需要访问自己的状态目录，本机权限或 app-server 问题会让第一步失败。
- 在只读沙箱下，macOS 工具链可能出现 `/tmp/xcrun_db-*` 相关 warning。
- 完整 Agent 会话有固定开销，即使小项目也可能消耗不少 tokens。

这些都不是 Loop 逻辑本身的问题，但会影响读者照做。

### 本章行动清单

- 找一个有测试的小项目。
- 写 `AGENTS.md`。
- 写 `TODO.md`。
- 先跑只读侦察。
- 只开放最小写权限。
- 用 Checker 验收。
- 人工确认后再开 PR。

## 第 7 章：失败案例：Loop 最容易在哪里失控

Loop 的风险通常不来自某一次错误输出，而来自错误被循环放大。

下面这些失败模式最常见。

### 失败一：目标太大

症状：

- Agent 一次改很多文件。
- 修 bug 变成重构。
- 输出很长，但没有清楚验收结果。

原因：

目标写成了“优化项目”“提升稳定性”“修一下 auth 模块”。

修法：

- 目标必须能写成 checklist。
- 第一个 Loop 只处理一个失败测试。
- 每轮只允许处理一个候选问题。

### 失败二：没有外部反馈

症状：

- Agent 说已经完成，但没有测试。
- 人需要重新检查所有结果。
- 循环每轮都在自我确认。

修法：

- 为每个 Loop 配一个反馈源。
- 没有测试时，先做只读分析，不进入自动修复。
- Checker 必须验证外部信号。

### 失败三：修改测试预期

症状：

- 测试通过了，但业务错误还在。
- diff 里出现测试预期被改。

修法：

- Maker prompt 明确写：未经人工批准，不要修改测试预期。
- Checker 必须检查测试文件是否被改。
- 高风险情况下先生成 patch 建议，不直接写入。

### 失败四：顺手重构

症状：

- 一个小 bug 牵出大量格式化、重命名、抽象封装。
- review 成本高于修复收益。

修法：

- 只允许修改和失败信号直接相关的文件。
- 无关重构直接打回。
- 每次运行后看 `git diff --stat`。

### 失败五：自动 merge

症状：

- Agent 修复后直接合并。
- 人只在出问题后才看到结果。

修法：

- 第一个 Loop 永远不要自动 merge。
- 最多生成 diff 和 PR 摘要。
- 合并前保留人工 review。

### 失败六：成本失控

症状：

- 小任务跑出多轮 Agent 会话。
- 没有失败上限。
- 没有“无事可做就沉默”的规则。

修法：

- 第一周每天一次。
- 先只读，再写入。
- 连续失败两次停止。
- 没有候选任务时只写一行状态。

### 断路器清单

| 断路器 | 推荐值 |
|---|---|
| 连续失败上限 | 2 次 |
| 单次运行时长 | 30 分钟 |
| 改动范围 | 相关文件 |
| 高风险动作 | 人工确认 |
| 无候选任务 | 不生成长报告 |

### 本章行动清单

- 给你的第一个 Loop 写 3 条停止规则。
- 写出 3 类必须交给人的动作。
- 在 Checker prompt 里加入 diff 范围检查。
- 给 token 成本设一个观察周期。

# 第四部分：把 Loop 变成个人系统

## 第 8 章：从工具使用者到系统设计者

Loop Engineering 最终服务的，不只是某个工具。

它服务的是个人系统。

在 Human3.0 的视角里，AI 时代的关键，是沉淀个人数字生产资料，而不是追逐工具更新。

什么是个人数字生产资料？

至少包括：

- 你的工作流。
- 你的模板。
- 你的项目规则。
- 你的评估标准。
- 你的素材库。
- 你的复盘。
- 你的自动化脚手架。

当你把一次任务做完，价值只发生一次。

当你把任务背后的规则写成 Skill、状态文件、模板和 Loop，价值会反复发生。

### 人的判断权

自动化越强，越要保留人的判断权。

| 事情 | 是否适合自动化 |
|---|---|
| 收集失败日志 | 适合 |
| 生成候选修复 | 适合 |
| 运行测试 | 适合 |
| 生成 PR 摘要 | 适合 |
| 合并到主分支 | 需要人确认 |
| 修改权限策略 | 需要人确认 |
| 删除生产数据 | 需要人确认 |
| 公开发布内容 | 需要人确认 |

这是一条责任边界。

Agent 可以帮你放大执行力，但责任仍然落在人身上。

### 从一次任务到可复用系统

每次任务结束后，问四个问题：

1. 哪些判断可以写成规则？
2. 哪些步骤可以写成模板？
3. 哪些状态应该留在模型外？
4. 哪些失败经验应该进入检查清单？

如果每次都能沉淀一点，你会逐渐拥有自己的 Agent 工作系统。

### 本章行动清单

- 把最近一次 AI 协作任务拆成步骤。
- 找出可以复用的 prompt。
- 找出可以写进 `AGENTS.md` 的规则。
- 找出一个可以做成 Loop 的低风险任务。

## 第 9 章：下一步：从 Codex Loop 到 Agent Harness

本书 v1.0 只把 Codex CI 修复 Loop 作为主实操。

这不是终点。

下一步可以有几个方向。

### Claude Code 版 Loop

Claude Code 的优势在于会话内上下文、任务调度和开发者体验。它适合单独展开一章，讲 `/loop`、scheduled tasks、`/goal` 和会话上下文管理。

但这些能力不能直接混进 Codex CLI 实操章。

工具不同，命令不同，边界不同。

### Cursor 版 Loop

Cursor 更接近日常 IDE 工作流。

它适合讨论：

- 如何把 Loop 嵌进编辑器。
- 如何做局部文件修复。
- 如何配合人工 review。
- 如何处理上下文选择。

### 自建 Agent Harness

当你需要更强的可控性时，可以考虑自建 Harness。

它适合这些场景：

- 多个 Agent 分工明确。
- 需要稳定任务队列。
- 需要审计日志。
- 需要权限隔离。
- 需要和内部系统深度集成。

但不要太早自建。

如果一个 `TODO.md`、一个 Maker prompt、一个 Checker prompt 已经能跑通，就先用简单方案。

### v2.0 候选方向

| 方向 | 价值 | 风险 |
|---|---|---|
| Claude Code CI Loop | 呼声高，适合续篇 | 工具版本变化快 |
| Cursor Loop | 贴近 IDE 用户 | 自动化能力边界要核实 |
| 自建 Harness | 可控性强 | 工程成本高 |
| 内容生产 Loop | 跨出编程场景 | 验收标准更难 |
| 项目维护 Loop | 长期价值高 | 成本和权限需要设计 |

### 本章行动清单

- 先跑通一个 Codex 最小 Loop。
- 再判断是否需要 Claude Code、Cursor 或自建 Harness。
- 不要为了工具而扩展系统。
- 每次扩展前，先写清楚新增能力解决什么问题。

## 结语

Loop Engineering 要解决一个很具体的问题：当 AI Agent 开始持续做事，人如何保留目标、反馈、边界和判断权。

如果你只写提示词，每次任务都会重新开始。

如果你开始设计 Loop，你就在把经验沉淀成系统。

这才是这本手册最想留下的东西。
