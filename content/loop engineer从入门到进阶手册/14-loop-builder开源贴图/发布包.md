### 03 为什么做这个工具

标题：

> 为什么要做 Loop Builder

正文：

1. 上下文缺失仍继续  
   缺目标图、失败日志或验收标准，Agent 只能猜。
2. 每轮没有外部反馈  
   没有测试、截图或数据，结果只剩自我确认。
3. 没有停止与确认规则  
   改动扩散、成本上涨，风险动作越过人。

结论：

> 先把执行方式设计清楚，再让 Agent 动手。

### 04 它如何工作

标题：

> 一句话进去，它先做 5 个判断

流程：

1. `Context Gate`：关键输入够不够
2. `Loop Fit`：Prompt、Checklist 还是 Loop
3. `Strategy`：选择合适的 Loop 模式
4. `Logic Confirmation`：人先确认执行逻辑
5. `Artifact`：生成 Prompt、Agent 或 Skill

说明：

> 缺少关键输入时停下来；逻辑确认后再生成正式产物。

### 05 它会生成什么

标题：

> 任务不同，产物也不同

决策表：

- 一次性任务 → Prompt
- 主要靠人验收 → Checklist
- 高风险动作 → Human-in-the-Loop
- 有反馈、需多轮修正 → 完整 Loop
- 同一业务反复运行 → 专用 Agent
- 跨项目长期复用 → 专用 Skill

结论：

> 优先生成当下够用的最轻产物。

### 06 四方分工

标题：

> 一套 Loop，四方各司其职

正文：

- Loop Builder：设计工作流，整理输入、反馈、停止与权限。
- Agent：执行任务，可以是 Codex、Claude Code 或 Cursor。
- Evaluator：用测试、截图、数据和规则提供验收证据。
- Human：确认执行逻辑、高风险动作和最终结果。

边界：

> 公开发布、merge、生产配置、权限与删除始终由人确认。

### 07 更多真实场景

标题：

> UI 复刻只是第一个公开案例

正文：

- CI 自动修复：失败日志 → 修复 → 测试 → 人工合并
- 内容专题生产：选题 → 草稿 → 审核 → 发布确认
- Skill 维护：规则候选 → 修改 → 验证 → 人工升级
- 学习复盘：输入 → 提炼 → 复习 → 更新记忆

结论：

> 先用一个真实任务跑通，再决定是否 Agent 化或 Skill 化。
