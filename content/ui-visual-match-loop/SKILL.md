# UI Visual Match Loop

## 来源

本 Skill 是由 `loop-builder` 生成的专用 Loop Skill。

生成链路：

```text
loop-builder
-> 识别场景：UI 视觉复刻 / 截图对比
-> 选择模式：Plan-Execute-Verify + Retry Loop + Human-in-the-Loop
-> 生成专用 Skill：ui-visual-match-loop
```

它不是 `loop-builder` 的替代品，而是 `loop-builder` 针对 UI 视觉复刻场景生成的可复用专用 Agent。

## 目标

把“按视觉稿复刻 UI”从来回口头反馈，变成一个可验证、可停止、可纠错的视觉闭环：

```text
目标视觉稿
-> 实现 UI
-> 启动页面
-> 截图
-> 对比差异
-> 修 Top 差异
-> 再截图
-> 达标或停止
```

本 Skill 不是普通 UI 编码提示词。它要求每轮都有截图证据、差异清单、修正范围和停止规则。

## 触发条件

用户出现以下意图时使用：

- 按这张视觉稿复刻页面
- Codex 复刻 UI 总是不像，帮我做成 Loop
- 对比目标图和当前页面截图，继续修 UI
- 用 Playwright 截图验收 UI
- 让页面更接近设计稿 / 截图 / Figma 导出的图
- 视觉还原、像素级对齐、UI 复刻闭环

如果用户提供的是 Figma URL，并且要求直接读取 Figma 设计上下文，优先结合已有 `figma-implement-design` skill。若用户提供的是图片或截图，本 Skill 可独立工作。

## 自然语言入口

用户不需要先填写完整任务卡。只要能描述：

```md
我想让 Codex 按这张图复刻页面。
目标图：<图片路径>
当前页面：<URL / 路由 / 启动命令>
```

然后本 Skill 自动补齐任务卡，并最多问 3 个关键问题。

## Intake 向导

先识别输入是否足够。

### 必需信息

- 目标视觉稿：图片路径、截图路径、Figma 截图或可访问目标页面截图。
- 当前页面入口：本地 URL、路由、页面文件，或启动命令。
- 技术栈：如 React、Vue、Next、Vite、静态 HTML、小程序 H5 预览。
- 验收视口：桌面、移动端，或二者都要。

### 缺少信息时最多问 3 个问题

优先问：

1. 目标视觉稿图片路径是什么？
2. 当前页面如何打开？例如 `npm run dev` 后的 URL 或具体路由。
3. 允许修改哪些文件？如果不确定，默认只改 UI 组件和样式文件。

其他信息使用安全默认值。

## 默认任务卡

当用户信息不足但可以推断时，使用以下默认值：

```md
任务目标：
让当前页面在指定 viewport 下尽量接近目标视觉稿。

成功标准：
- 页面主要布局、层级、尺寸、颜色、字号、间距、圆角、阴影与目标图接近。
- 每轮截图后输出 Top 5 差异。
- 每轮 Maker 只修 Top 3 差异。
- 最终由用户确认是否达标。

反馈信号：
- Playwright / 浏览器截图。
- 目标图与当前截图的视觉差异清单。
- 用户人工确认。

允许动作：
- 读取目标图和项目 UI 文件。
- 修改页面、组件、样式、静态资源引用。
- 启动本地开发服务。
- 使用 Playwright 或项目已有截图工具截图。

禁止动作：
- 不改业务逻辑、接口、权限、支付、数据删除、生产配置。
- 不引入新 UI 库，除非用户确认。
- 不重构无关模块。
- 不为了视觉复刻删除核心交互。
- 不自动发布。

人工确认节点：
- 是否接受最终视觉差异。
- 是否引入新依赖或 UI 库。
- 是否修改业务逻辑。
- 是否提交、发布或部署。
```

## Loop 策略

主模式：Plan-Execute-Verify。

辅助模式：

- Retry Loop：每轮基于截图差异修正。
- Human-in-the-Loop：最终视觉判断和高风险改动由用户确认。

为什么适合完整 Loop：

- 有明确目标图。
- 有当前截图作为反馈。
- 可以每轮修正差异。
- 可以通过最大轮次、差异阈值、人工确认停止。

为什么不是普通 Prompt：

- 普通 Prompt 只能一次性生成 UI。
- 视觉差异需要截图反馈。
- 每轮都要对比目标图和当前图，按优先级修正。

## 固定流程

### 1. Planner：拆视觉稿和项目入口

只读，不改文件。

输出：

- 目标图路径。
- 当前页面入口。
- 技术栈和相关文件。
- viewport。
- 视觉拆解：布局、层级、组件、颜色、字体、间距、圆角、阴影、图片资产。
- 风险和禁止动作。
- Maker 第一轮最小任务。

### 2. Maker：实现或修正 Top 差异

只改允许范围内的 UI 文件。

要求：

- 每轮最多修 3 个视觉差异。
- 优先修布局、尺寸、间距、颜色这些高影响差异。
- 不改业务逻辑。
- 不做无关重构。
- 修改后说明改了哪些文件和原因。

### 3. Screenshot Checker：启动页面并截图

使用项目已有方式启动页面。若需要 Playwright：

- 优先使用已安装的项目工具。
- 如果全局安装了 `playwright` skill，可按该 skill 的 wrapper 使用。
- 不强行安装新依赖；需要安装时先问用户。

输出：

- 截图路径。
- viewport。
- 页面 URL。
- 截图是否非空。
- 是否有明显加载失败、资源缺失、报错遮挡。

### 4. Visual Evaluator：对比目标图和当前截图

输出 Top 5 差异，按优先级排序：

| 优先级 | 差异类型 | 目标表现 | 当前表现 | 建议修法 |
| --- | --- | --- | --- | --- |
| P1 | 布局 / 尺寸 / 间距 / 颜色 / 字体 / 圆角 / 阴影 / 资源 / 响应式 |  |  |  |

判断：

- 通过：进入人工确认。
- 未通过：给 Maker 下一轮 Top 3 修正任务。
- 不确定：请求用户确认。
- 越界：停止。

### 5. Evaluator：决定继续或停止

继续条件：

- Top 差异仍然明确。
- 修改范围仍在 UI 文件内。
- 未超过最大轮次。
- 用户没有要求停止。

停止条件：

- 用户确认达标。
- 达到最大轮次，默认 3 轮。
- 连续 2 轮同类差异没有改善。
- 需要改业务逻辑或引入新依赖但用户未确认。
- 页面截图无法生成或目标图不可读。
- 剩余差异进入主观审美区。

## 角色 Prompt 模板

### Planner Prompt

```md
你是 UI Visual Match Planner，只做只读分析，不修改文件。

任务：
按目标视觉稿复刻当前页面。

输入：
- 目标图：<path>
- 当前页面：<url or route>
- 技术栈：<stack>
- viewport：<desktop/mobile/both>
- 允许修改：<paths>

请输出：
1. 项目入口和相关 UI 文件。
2. 目标视觉稿拆解：布局、组件、字体、颜色、间距、圆角、阴影、资源。
3. 当前页面可能需要修改的区域。
4. 第一轮 Maker 只应处理的 Top 3 任务。
5. 截图验收方式。
6. 禁止动作和人工确认点。
```

### Maker Prompt

```md
你是 UI Visual Match Maker，只按本轮 Top 3 差异做最小 UI 修改。

要求：
1. 只改允许范围内的 UI 组件、样式和静态资源引用。
2. 不改业务逻辑、接口、权限、支付、数据删除、生产配置。
3. 不引入新 UI 库，除非用户确认。
4. 不做无关重构。
5. 修改后说明改动文件和对应差异。
```

### Screenshot Checker Prompt

```md
你是 Screenshot Checker，只负责启动页面和截图，不评价审美。

请检查：
1. 页面是否能打开。
2. 目标 viewport 是否正确。
3. 截图是否非空、无遮挡、无加载失败。
4. 保存截图路径。
5. 报告命令、URL、viewport 和阻塞问题。
```

### Visual Evaluator Prompt

```md
你是 Visual Evaluator，负责对比目标图和当前截图。

输入：
- 目标图：<path>
- 当前截图：<path>
- viewport：<size>

请输出：
1. 是否接近目标图。
2. Top 5 视觉差异，按优先级排序。
3. 每个差异的建议修法。
4. 下一轮 Maker 只修 Top 3。
5. 是否继续、停止或等待人工确认。
```

## 边界

- 不承诺像素级完全一致，除非目标图、资源、字体、viewport 和项目约束都明确。
- 不把主观审美差异伪装成客观错误。
- 不自动安装依赖。
- 不自动提交、发布或部署。
- 不改业务逻辑来迁就视觉。
- 目标图不可读、当前页面打不开或截图不可生成时，先停止并报告阻塞。
