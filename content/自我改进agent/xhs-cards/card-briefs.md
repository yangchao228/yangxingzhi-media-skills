# 第一季小红书图文卡片 brief

## 01 Agent 自我改进的 5 个真相

封面标题：Agent 会自己变强吗？先看这 5 个条件

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | Agent 会自己变强吗 | 先别急着兴奋，真正的自改进有条件。 |
| 02 | 多试几次不叫成长 | 反复生成答案，只是采样；行为模式改变，才接近自改进。 |
| 03 | 第一个条件：可验证 | 结果能判断对错，Agent 才知道该往哪里改。 |
| 04 | 第二个条件：有反馈 | 测试、评分、人审、日志，都比一句“不错”更有用。 |
| 05 | 第三个条件：能沉淀 | 经验要写成 Skill、模板、规则或错题本。 |
| 06 | 第四个条件：有外环 | 日常执行是一层，定期复盘和更新规则是另一层。 |
| 07 | 第五个条件：人审核 | 没有人审的自改进，容易把错误写成长期规则。 |
| 08 | 先建一个错题本 | 想让 Agent 长记性，先记录它在哪里失败。 |

发布配文方向：很多人把“Agent 自我改进”想成科幻，其实第一步很朴素：让失败留下来。

## 02 内环/外环双循环图解

封面标题：会跑 Loop，不代表 Agent 会成长

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | 会跑 Loop 不等于会成长 | Agent 一直执行，只说明它在循环，不说明它在进步。 |
| 02 | 内环负责做事 | 目标、工具、验证、继续或停止。 |
| 03 | 外环负责学习 | 读日志、找重复失败、生成规则更新建议。 |
| 04 | 真正关键是写回资产 | Skill、模板、SOP、Memory，才会影响下一次。 |
| 05 | 为什么 Skill 适合进化 | 它是文件，能 diff，能审查，能回滚。 |
| 06 | 什么时候启动外环 | 同类错误重复出现，或人工纠偏反复发生。 |
| 07 | 什么时候不要改规则 | 一次性失败、来源不清、验证不充分，都先别沉淀。 |
| 08 | 下一步：建反馈日志 | 外环需要燃料，燃料就是可读的失败记录。 |

发布配文方向：Loop 解决持续执行，外环解决经验沉淀。

## 03 给 Agent 用的错题本模板

封面标题：先别谈自进化，给 Agent 建个错题本

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | Agent 不长记性怎么办 | 先别改模型，先改记录方式。 |
| 02 | 聊天记录不是经验 | 没有分类、证据和下一次规则，失败很快会被冲掉。 |
| 03 | 错题本记录 6 件事 | 目标、预期、实际、证据、失败类型、下次规则。 |
| 04 | pass/fail 比打分更稳 | “7 分”很模糊，“测试没过”才可执行。 |
| 05 | 失败要分类 | 事实错、范围越界、验证不足、风格跑偏、权限风险。 |
| 06 | 下一轮怎么用 | 任务开始前加载相关失败，不加载整本历史。 |
| 07 | 别什么都写进长期规则 | 临时偏好、一次性情绪、偶发错误不要沉淀。 |
| 08 | 收藏模板 | 评论“错题本”，领取 Agent 反馈日志模板。 |

发布配文方向：Agent 不是不会学，是很多时候我们没有把失败整理成它能用的格式。

## 04 个人 Agent 自改进架构图

封面标题：让 Agent 每天复盘自己，最小系统这样搭

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | 个人 Agent 怎么长记性 | 不从全自动开始，从每日复盘开始。 |
| 02 | 最小系统只要 4 个文件 | 反馈日志、Skill、审核表、变更记录。 |
| 03 | 内环：日常任务执行 | 写作、巡检、整理、排障，每次留下结果。 |
| 04 | 外环：每日复盘 | 读取日志，找重复失败，提出 Skill 更新。 |
| 05 | 人审：决定是否合并 | Agent 给建议，人决定规则是否进入长期资产。 |
| 06 | 回滚：保留版本 | Skill 更新要能撤回，不能只往前堆。 |
| 07 | 先选低风险任务 | 内容诊文、周报整理、项目巡检，比生产操作更适合起步。 |
| 08 | 下周试一次 | 先让一个 Agent 连续 7 天复盘同一类任务。 |

发布配文方向：自改进可以很朴素：任务执行后留日志，第二天让 Agent 复盘，人审后更新规则。

## 05 自改进 Agent 的 7 条安全边界

封面标题：没有验证的自改进，只是在漂移

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | 没有验证，只是在漂移 | Agent 改得越勤，不代表越接近正确。 |
| 02 | 边界 1：目标可验收 | 不要让 Agent 优化一个说不清的目标。 |
| 03 | 边界 2：反馈有证据 | 日志、测试、diff、人工批注要留痕。 |
| 04 | 边界 3：连续失败暂停 | 同样失败两次，就该停下来查原因。 |
| 05 | 边界 4：敏感动作人审 | 发布、删除、支付、生产配置，都不自动放行。 |
| 06 | 边界 5：更新可 diff | Skill 修改必须看得出改了什么。 |
| 07 | 边界 6-7：可回滚，留不确定性 | 错误规则要能撤回；高风险判断别写死。 |
| 08 | 把判断权留给人 | Agent 负责执行和复盘，人负责边界和方向。 |

发布配文方向：自改进需要边界、证据和回滚机制，不能只给 Agent 更多自由。

## 06 失败怎么变成 Skill

封面标题：Agent 失败一次，能不能自动长一个技能？

| 页码 | 标题 | 正文要点 |
| --- | --- | --- |
| 01 | 失败能不能变成 Skill | 这个问题值得测，但不能直接相信宣传。 |
| 02 | 工具想解决什么 | 从失败轨迹里提炼可复用规则。 |
| 03 | 先选低风险任务 | 不拿生产操作做第一轮实验。 |
| 04 | 看三个输出 | 规则是否准确、是否过拟合、是否能迁移。 |
| 05 | 跟手写 Skill 比 | 自动提炼快，但人更懂边界和语境。 |
| 06 | 不能跳过审核 | 工具生成的 Skill，也要 diff、人审、回滚。 |
| 07 | 是否接入个人系统 | 看稳定性、可解释性和维护成本。 |
| 08 | 等实测结论 | 评论“EvoSkill”，后续放完整测试记录。 |

发布配文方向：工具测评要回到一个问题：它能不能降低下一次的失败成本。
