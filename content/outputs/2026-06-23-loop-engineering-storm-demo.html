Demo 说明

这次如何使用 storm-research

本 demo 把「Loop Engineering 是否真的提效？」作为研究对象，按 `storm-research` 协议先拆视角，再找冲突，最后输出研究简报、可信度评审和可继续核验的采证清单。这里展示的是研究结构，不是公众号正文。

输入

本地 Loop Engineering 手册素材、CI 自动修复篇、三角色架构篇、STORM 方法稿。

协议

多视角扫描、矛盾地图、研究简报、可信度评审、后续采证计划。

约束

不把角色模拟当事实，不输出公开结论，不替代事实核查。

交接

给出 content_state 和 handoff，便于进入事实采证。

多视角扫描

五个视角拆开看提效问题

同一个问题放到不同位置，会得到不同的判断。`storm-research` 的第一步是把“提效”拆成可验证、可质疑、可计成本的多个问题。

实践者

核心关切

是否少盯 CI、少重复排障、少手动汇总状态。

支持判断

CI 失败、部署状态、open issues 巡检这类任务适合 loop。

待查问题

两周内节省多少人工时间，误报和人工接管次数是多少。

学者

核心关切

提效是否可测，质量和失败率是否一起纳入。

支持判断

可用 lead time、intervention rate、rollback rate、token spend 评估。

待查问题

是否有论文或生产案例量化 agentic workflow 的收益。

怀疑者

核心关切

自动化是否掩盖了后续人工验收、权限和回滚负担。

支持判断

低风险检查可以自动化，高代价动作要人负责。

待查问题

误修率、重复失败、上下文漂移和生产事故如何被控制。

经济观察者

核心关切

省下的人时是否高于 token、订阅、维护和风险成本。

支持判断

高频、低风险、可验证任务能摊薄配置成本。

待查问题

一次 Maker + Checker loop 的平均成本和失败成本是多少。

历史观察者

核心关切

它和 cron、CI/CD、RPA、DevOps 的连续性。

支持判断

AI 加入计划、生成、评估和沉淀，可靠性仍依赖日志和回滚。

待查问题

哪些 DevOps 治理经验可以直接迁移到 Agent loop。

矛盾地图

真正有价值的判断在冲突处

冲突 支持侧 挑战侧 当前判断
自动执行 vs 人工判断 CI 巡检、失败分类、状态汇总可以自动化。 生产配置、权限、数据删除、merge 必须人工确认。 自动化低风险动作，高代价动作设置人工节点。
提效 vs 成本转移 少盯盘、少复制日志、少重复跑命令。 token、误修、排障、审批和维护成本会吞掉收益。 用总成本判断效率，不能只看 Agent 跑了几步。
连续运行 vs 错误放大 Automations 和定时巡检让 loop 有心跳。 长期运行会暴露上下文漂移、重复失败和结构退化。 要配最大轮数、单次时长、diff 范围、失败上限和日志。
通用 Agent vs 窄场景模板 通用 Agent 可处理多样任务。 第一个 loop 应从明确、可测试、有边界的小任务开始。 先做窄场景，稳定后再组合模式。

共识底座

  • 重复、可验证、可回滚、低风险任务最适合进入 loop。
  • CI 自动检查与修复是合适的第一个 demo。
  • 生成和验证需要分离。

证据最弱

“具体提效幅度”仍弱。当前素材能支持提效潜力和成立条件，不能支持团队级 ROI 百分比。

关键盲点

普通团队维护成本、长期代码质量影响、多模型分工 ROI、定时巡检噪音率和责任归属。

研究简报

核心发现与行动建议

研究简报把前面的视角和矛盾压缩成可行动的判断。这里区分事实、推断和观点，避免把未经采证的内容写成发布结论。

隐藏连接

`storm-research` 和 Loop Engineering 都把 AI 输出组织成人可审计的工作流：前者用于研究，后者用于执行。共同价值是让人的判断权回到关键节点。

行动建议

先做两周只读 CI 侦察 loop，记录命中率、误报率、token 成本和人工接管次数，再决定是否进入自动修复。

前沿问题

当 Agent 系统具备长期记忆、可配置 skill、多模型评估和自动化调度后，团队如何定义“人仍然必须决策的节点”？这个问题会影响效率上限、安全边界和责任归属。

最弱结论

“Loop Engineering 能带来多大幅度的效率提升”。当前素材支持提效潜力和成立条件，不能支持具体百分比。

偏见检查

  • 工程乐观偏见
  • 编程场景偏见
  • 高技能用户偏见
  • 工具可用性偏见

缺失视角

建议补安全 / 合规负责人视角，重点看授权、审计、责任和事故处置。

必须人工核验项

官方工具能力和限制、论文与报道原始来源、真实 CI loop 执行日志、token 与人工成本记录、提效指标定义。

后续采证计划

进入深度事实核查前要查什么

P0
官方工具能力和限制

建议来源：Claude Code 官方文档、OpenAI Codex 官方文档。目标输出：产品事实卡片和跨工具对照表。

P0
真实 CI loop 效率账本

建议来源：本地 CI 记录、token 使用记录、人工 review 记录。目标输出：两周小样本效率账本。

P1
长周期 coding agent 质量退化

建议来源：论文 PDF、代码 benchmark、复现实验。目标输出：反向证据卡。

P1
Maker / Checker 分工效果

建议来源：自建对照实验、PR review 记录。目标输出：质量评估表。

P2
普通团队维护成本与禁入清单

建议来源：访谈、开源仓库 issue、安全规范、事故复盘。目标输出：失败场景清单和禁入清单。

下一步建议

建议进入深度事实核查

原因很简单：当前 `storm-research` 已经找到了问题地图、冲突点和最弱结论，但公开写作需要一手来源和真实数据。下一步应核验官方文档、论文、生产案例，并做一个两周 CI 侦察 loop 小样本。

最小事实核查任务

用一个真实仓库跑只读 CI 侦察 loop，记录候选命中率、误报率、token 成本、人工接管次数和节省时间。拿到这组数据后，再决定是否写成公众号案例。

推荐：进入

但只围绕 CI 自动检查与修复这个窄场景，不扩成泛泛的 AI 提效话题。
