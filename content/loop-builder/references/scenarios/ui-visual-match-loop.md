# UI 视觉复刻 Loop

## 定位

用于把“按视觉稿复刻 UI”设计成可验证、可停止、可纠错的视觉闭环。

适用对象：

- 按截图复刻页面。
- 按 Figma 导出图还原页面。
- Codex 多轮改 UI 但总是不像，需要截图反馈闭环。
- 前端页面视觉验收。
- 目标图和当前页面需要逐轮缩小差异。

## Loop 适配判断

- 结论：通常适合完整 Loop。
- 推荐主模式：Plan-Execute-Verify。
- 可组合模式：Retry Loop、Human-in-the-Loop。
- 原因：
  - 有目标视觉稿。
  - 有当前页面截图作为反馈。
  - 每轮能生成差异清单。
  - Maker 可以按 Top 差异修正。
  - Checker 可以截图验收。
  - Evaluator 可以决定继续、停止或交给人。

## 和普通 Prompt 的区别

普通 Prompt：

```text
按这张图复刻页面。
```

容易出现的问题：

- Codex 看不到真实运行截图。
- 用户只能口头反馈“还不像”。
- 每轮修改没有优先级。
- 容易顺手改业务逻辑。

UI 视觉复刻 Loop：

```text
目标图 -> 实现 -> 截图 -> 差异清单 -> 修 Top 3 -> 再截图 -> 达标或停止
```

## 最小 Loop 设计卡

| 字段 | 内容 |
|---|---|
| 目标 | 当前页面在指定 viewport 下接近目标视觉稿 |
| 输入 | 目标图、当前页面入口、技术栈、viewport、允许修改范围 |
| 状态 | `<业务目录>/ui-visual-match-state.md` |
| 执行者 | Planner / Maker / Screenshot Checker / Visual Evaluator / Evaluator |
| 验收者 | 截图证据 + 用户人工确认 |
| 反馈信号 | 目标图、当前截图、Top 差异清单 |
| 停止规则 | 达标、最大轮次、连续无改善、越界、需要人工确认 |
| 人工确认节点 | 引入新依赖、改业务逻辑、提交、发布、接受最终视觉差异 |
| 禁止动作 | 不改业务逻辑、接口、权限、支付、数据删除、生产配置 |

## 默认 Intake

用户最小输入：

```md
帮我复刻这个 UI 视觉稿
```

UI 复刻不要使用固定问题清单。先由模型判断用户已经提供了什么，再区分必需、可默认和后置确认。

目标视觉稿通常是最关键的运行期输入，但是否在本轮强制提供，取决于决策依赖 Gate：

- 如果本轮要基于具体视觉稿判断复杂度、最大轮次、风险或生成可执行 Prompt，目标视觉稿是必需输入。
- 只有用户明确要求通用 Skill 协议草案，或明确接受先不基于真实视觉稿校准时，才可以不提供目标视觉稿；此时必须标注“未基于真实视觉稿校准”。
- 不能因为任务名是 UI 复刻就自动跳过依赖判断，也不能把目标视觉稿硬编码为所有构建期任务的必填项。

前置补问规则：

- 如果用户已上传图片或给出本地图片路径，不问前置问题，直接进入任务卡和工作逻辑确认卡；用户确认前不能生成执行 Prompt，也不能开始项目侦察、截图、运行命令或改代码。
- 如果模型判断没有可用目标图，目标视觉稿就是必需输入，需要请求用户补充。
- 当前页面入口通常是可默认信息：让 Codex 在项目内只读侦察启动命令、路由和页面文件。
- 允许修改范围通常是后置确认：默认只改 UI 组件、页面文件和样式文件；越界时再请求用户确认。

## 推荐输出

如果用户只是说“帮我复刻这个 UI 视觉稿”，默认输出“给 Codex 使用的 UI 复刻 Loop Prompt”，不是专用 Skill。

这个 Prompt 必须让 Codex 能直接执行当前任务：

- 先只读分析目标图。
- 输出页面结构、组件树、设计 tokens、字体、间距、圆角、阴影、图片和图标资产。
- 制定实现计划。
- 分阶段实现。
- 运行页面并截图。
- 对比目标图和当前截图。
- 每轮只修 Top 3 差异。
- 输出最终差异清单和人工精修建议。

如果用户明确说“以后在多个项目长期使用”“生成 Skill”“全局安装”，再进入专用 Skill 路线：

```text
content/ui-visual-match-loop/
  SKILL.md
  skill.json
```

生成专用 Skill 前，不要直接输出 `SKILL.md`。必须先按 `references/skill-generation-contract.md` 输出场景工作流分析、Skill 协议草案和过渡 Prompt。

## 生成专用 Skill 前的工作流建模

UI 视觉复刻类 Skill 的专业角色不是“自由发挥的设计师”，而是“高级前端还原工程师”。

Skill 协议草案必须包含以下硬规则：

- 先不要写代码。
- 先只读分析目标视觉稿。
- 设计分析必须覆盖：
  - 页面结构。
  - 组件树。
  - 颜色 tokens。
  - 字号、字重、行高。
  - 间距系统。
  - 圆角、阴影。
  - 图片和图标资产。
- 再制定实现计划。
- 实现时分阶段推进：
  - layout。
  - header。
  - hero。
  - card / list / form。
  - responsive。
- 每个阶段实现后运行项目并截图。
- 对比目标视觉稿和当前截图，列出视觉差异。
- 每轮优先修正影响最大的 3 个差异。
- 不一次性大改。
- 不自行改变设计风格。
- 无法判断某个值时，使用最接近的 CSS 值，并在报告里标注不确定项。

验收重点：

- 1440px 宽度下视觉相似度优先。
- 布局、字体、颜色、间距、圆角、阴影尽量接近。
- 最终输出差异清单和剩余人工精修建议。

## 给 Codex 使用的 Prompt 骨架

当用户只要完成当前 UI 复刻任务时，输出类似下面的 Prompt，补齐已知材料，占位缺失信息：

```md
你现在是高级前端还原工程师，不是自由发挥的设计师。

任务：
根据目标 UI 视觉稿，高保真复刻当前页面。

输入：
- 目标视觉稿：<目标图路径或已附图>
- 当前页面：优先使用用户给出的 URL / 路由 / 启动命令；未提供时先在当前项目只读侦察
- 技术栈：先在当前项目自动识别
- 验收 viewport：1440px 优先
- 允许修改：默认只改 UI 组件和样式文件

工作流：
1. 先不要写代码，只做设计分析。
2. 在当前项目只读侦察技术栈、启动命令、路由和相关页面文件。
3. 输出页面结构、组件树、颜色 tokens、字号/字重/行高、间距系统、圆角/阴影、图片和图标资产。
4. 制定实现计划，按 layout / header / hero / card-list-form / responsive 分阶段推进。
5. 每阶段修改后运行项目并截图。
6. 对比目标视觉稿和当前截图，列出 Top 5 视觉差异。
7. 每轮只修影响最大的 Top 3 差异。
8. 无法判断的值用最接近 CSS 值，并在报告里标注不确定项。

禁止动作：
- 不改业务逻辑。
- 不引入新 UI 库，除非用户确认。
- 不自动提交，不自动发布。
- 不自行改变设计风格。
- 不一次性大改。

停止规则：
- 用户确认达标。
- 达到本次任务经复杂度分析后设定的最大轮次。
- 连续 2 轮同类差异无改善。
- 需要改业务逻辑或引入新依赖。
- 页面无法截图或目标图不可读。

最终输出：
- 修改文件清单。
- 每轮截图路径。
- 差异清单。
- 剩余人工精修建议。
```

## 断路器

- 最大轮次必须由复杂度分析得出：综合页面复杂度、反馈成本、修改风险、可回滚性和用户预算，不使用场景默认值。
- 每轮只修 Top 3 差异。
- 连续 2 轮同类差异没有改善则停止。
- 目标图不可读或当前页面无法截图则停止。
- 需要改业务逻辑或引入新依赖时等待用户确认。
- 剩余差异进入主观审美区时等待用户确认。

## 可抽象回 loop-builder 的规则候选

- UI 复刻类任务适合完整 Loop，而不是单次 Prompt。
- 视觉反馈必须来自真实截图，不能只靠自然语言描述。
- Maker 每轮只修 Top 3 差异，避免发散。
- Visual Evaluator 与 Maker 职责分离。
