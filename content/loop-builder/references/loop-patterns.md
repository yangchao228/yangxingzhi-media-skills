# Loop 模式参考

本文件用于选择 Loop 模式。每次设计 Loop 时，先判断任务反馈是否足够清晰，再选择主模式。

## 模式总览

| 模式 | 适用场景 | 不适用场景 | 主要风险 | 升级方向 |
| --- | --- | --- | --- | --- |
| Retry Loop | 失败原因明确、修复动作小、验收信号稳定 | 目标模糊、一次失败可能来自多处原因 | 重复消耗 token，掩盖根因 | 加 Checker 或断路器 |
| Plan-Execute-Verify | 有明确目标、需要拆解、每步可验收 | 没有验收标准、需求持续变动 | 计划过大，执行偏航 | 拆成多个小 Loop |
| Explore-Narrow | 选题、方案、排障、研究、素材扫描 | 已有明确修复路径 | 探索发散，难以收口 | 增加候选上限和筛选表 |
| Human-in-the-Loop | 高风险动作、价值判断、生产权限、发布决策 | 低风险重复任务 | 人工节点过多导致阻塞 | 把低风险部分拆出自动化 |
| Lifecycle Loop | 长期维护、内容栏目、项目巡检、知识库更新 | 单次任务、无状态任务 | 状态污染、成本累积 | 引入日志、归档、周期复盘 |

## 典型任务映射

| 用户任务 | 推荐主模式 | 辅助模式 | 默认处理 |
| --- | --- | --- | --- |
| CI 失败修复 | Plan-Execute-Verify | Retry Loop | 先只读侦察错误日志，再由 Maker 最小修复，Checker 跑验收命令 |
| 公众号选题 | Explore-Narrow | Human-in-the-Loop | 先生成候选池和评分表，最后由用户确认选题 |
| 生产权限配置改动 | Human-in-the-Loop | Plan-Execute-Verify | 只输出方案、风险、回滚和确认卡，执行前必须用户确认 |
| 学习复盘 | Lifecycle Loop | Human-in-the-Loop | 建状态文件、复盘清单和周期节奏，用户确认长期方向 |
| 项目维护巡检 | Lifecycle Loop | Plan-Execute-Verify | 固定周期读取状态、跑检查、输出风险和下一步 |

## Retry Loop

### 解决什么问题

用于处理“尝试一次失败后，可以基于错误反馈做小步修复”的任务。

典型例子：

- 单元测试失败后的最小修复
- lint 报错修复
- 文档链接检查失败后的链接修复
- 图片上传失败后的路径修正

### 适合场景

- 错误信号清楚，例如测试日志、编译错误、校验报告。
- 每轮修改范围小。
- 成功标准可以由工具给出。
- 失败后可以安全回滚。

### 不适合场景

- 失败原因需要业务判断。
- 任务可能触碰生产配置、权限、支付、用户数据。
- 修改范围跨多个模块，且没有明确验收路径。

### 最小结构

1. 读取当前错误。
2. 只改与错误直接相关的最小范围。
3. 跑同一条验收命令。
4. 记录本轮动作和结果。
5. 达到成功、轮次上限或高风险信号后停止。

### 停止条件

- 验收通过。
- 连续 2 轮同类失败。
- 修改范围超出预设目录。
- 测试被修改但没有人工确认。
- token 或时间超过预算。

## Plan-Execute-Verify

### 解决什么问题

用于把复杂任务拆成计划、执行、验收三段，避免 Agent 一口气改完后难以判断质量。

典型例子：

- CI 修复
- 小功能实现
- 文档结构重写
- 数据清洗流程
- 项目维护任务

### 适合场景

- 目标能写成验收标准。
- 任务可以分解为 3 到 7 个步骤。
- 每一步有可观察输出。
- 用户愿意在关键点确认。

### 不适合场景

- 需求还没有成形。
- 没有任何外部反馈。
- 成功标准主要来自审美、价值判断或商业取舍。

### 最小结构

1. Planner 只读侦察并生成计划。
2. Maker 按计划执行最小修改。
3. Checker 跑测试、lint、构建或人工可读验收。
4. Evaluator 判断是否继续、回滚、交给用户。

### 停止条件

- 验收通过。
- Checker 发现风险超出 Maker 权限。
- 计划连续两次需要大幅改写。
- 用户确认点未通过。

## Explore-Narrow

### 解决什么问题

用于先扩大搜索范围，再收敛到少数高价值候选。

典型例子：

- 公众号选题池
- 技术方案选型
- 排障方向扫描
- 学习资料筛选
- 产品机会发现

### 适合场景

- 起点模糊，但有明确筛选标准。
- 需要比较多个候选。
- 结果最终需要人工判断。

### 不适合场景

- 已经有明确目标和唯一执行路径。
- 候选无法验证，只能靠主观偏好。
- 没有时间或来源预算。

### 最小结构

1. Explorer 生成候选池。
2. Narrower 按评分表收敛。
3. Checker 抽样核对来源、事实或约束。
4. 用户确认最终候选。

### 停止条件

- 候选达到上限。
- 评分最高候选仍低于门槛。
- 关键来源不足。
- 用户确认方向。

## Human-in-the-Loop

### 解决什么问题

用于把低风险步骤交给 Agent，把高风险判断留给人。

典型例子：

- 生产配置变更前的方案和风险清单
- 商业发布前的投稿材料检查
- PR merge 前的摘要和测试证据整理
- 用户数据处理前的影响评估

### 适合场景

- 存在不可逆或高影响动作。
- 成功标准涉及价值判断。
- 工具可以准备证据，但不能代替用户拍板。

### 不适合场景

- 每一步都需要用户确认，导致系统无法推进。
- 任务没有可拆出的低风险部分。

### 最小结构

1. Agent 只做侦察、方案、差异整理。
2. 输出人工确认卡。
3. 用户确认后，Agent 执行被授权的低风险步骤。
4. 最终动作再次要求用户确认。

### 停止条件

- 用户未确认。
- 发现权限、数据、生产、支付、公开发布相关动作。
- 输出证据不足。

## Lifecycle Loop

### 解决什么问题

用于长期维护某个资产，让任务从一次性完成变成可持续更新。

典型例子：

- 每周项目健康检查
- 内容选题库维护
- 学习复盘
- 电子书素材归档
- 失败案例库更新

### 适合场景

- 有稳定周期。
- 有状态文件或日志。
- 每轮都能产生可沉淀资产。
- 用户能定期复盘。

### 不适合场景

- 任务只需要一次交付。
- 状态来源混乱。
- 反馈信号无法被记录。

### 最小结构

1. 读取上轮状态。
2. 执行本轮最小任务。
3. 更新状态、日志、风险和下一步。
4. 定期复盘是否继续、暂停、升级或废弃。

### 停止条件

- 连续多轮没有新增价值。
- 成本超过产出。
- 状态文件失真。
- 用户取消该循环。

## 组合规则

优先选择一个主模式，再组合一个辅助模式。

常见组合：

- CI 修复：Plan-Execute-Verify + Retry Loop
- 内容选题：Explore-Narrow + Human-in-the-Loop
- 项目维护：Lifecycle Loop + Plan-Execute-Verify
- 学习复盘：Lifecycle Loop + Human-in-the-Loop
- 生产变更准备：Human-in-the-Loop + Plan-Execute-Verify

## 工具边界

- Codex 适合本地代码、文件、测试、构建、Git 工作流中的设计和执行。
- Claude Code、Cursor、其他 IDE Agent 适合各自工具环境内的代码协作，具体能力以用户当前版本和本机配置为准。
- 自建 Harness 适合多工具编排、长期状态、权限控制、日志审计和评估器固化。
- 任何工具都不能跳过用户对高风险动作的确认。
