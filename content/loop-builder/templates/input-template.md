# Loop Intake 任务卡模板

本模板由 `loop-builder` 使用，用来先做 Context Gate，再把用户的自然语言任务整理成可确认的任务卡。不要把整张表直接丢给用户填写。

## 使用原则

- 先从用户原文、对话上下文、文件路径和当前工作目录自动抽取。
- 缺失字段用 `<待确认>`，不要编造。
- 缺失的必需信息全部补问，且本轮停止等待用户回复；可默认信息按优先级最多展示 5 个，后置确认不阻塞用户。
- 必需信息不只来自任务类型，还来自本轮关键判断的证据依赖。
- Context Gate 通过后，才判断是否值得进入 Loop 和产物类型。
- 任务卡需要用户能一眼看懂，不要写成内部工程字段堆砌。

## 决策依赖检查

先列出本轮准备做的关键判断，再判断这些判断依赖哪些证据。构建 Loop 默认要基于当前具体任务判断复杂度、最大轮次、风险和执行策略；缺少会影响这些判断可靠性的证据时，必须列为必需信息并停止。

```md
## 决策依赖检查

| 本轮关键判断 | 需要的证据 | 当前是否具备 | 处理 |
|---|---|---|---|
| 是否适合 Loop |  | 是 / 否 | 继续 / hard stop / 标注未校准 |
| 推荐产物类型 |  | 是 / 否 | 继续 / hard stop / 标注未校准 |
| 复杂度和最大轮次 |  | 是 / 否 | 继续 / hard stop / 标注未校准 |
| 风险和禁止动作 |  | 是 / 否 | 继续 / hard stop / 标注未校准 |
| 工作流阶段 |  | 是 / 否 | 继续 / hard stop / 标注未校准 |
```

判断规则：

- 如果用户要求基于具体任务、样本、故障、材料或实际运行情况做判断，相关材料就是必需输入。
- 只有用户明确要求通用框架、通用模板，或明确接受先不基于真实样本校准时，才可以继续；否则缺少样本必须 hard stop。
- 不能把某个场景的字段硬编码为所有任务的必填项；必填项必须来自本轮关键判断。

## 缺失信息分级

先分级，再决定是否补问：

| 缺失信息 | 分级 | 处理方式 | 原因 |
| --- | --- | --- | --- |
|  | 必需 / 可默认 / 后置确认 | 补问 / 默认 / 执行中确认 |  |

只对“必需”信息生成补问，不限制数量。若存在必需缺失，本轮只输出补问卡，不输出任务卡、Loop 适配判断、自动产物选择、最终 Prompt、Skill 化建议、Skill 协议或 Loop 包。可默认信息最多展示 5 个默认处理方式，不要写成强制问题。

## 阻塞补问卡

```md
## 请先补充
我已经完成 Intake，但缺少必需信息，暂时不能继续生成方案。

已识别：
- 场景：
- 目标：

缺失必需信息：
1. <必需问题>（影响：<为什么没有它无法继续>）

你可以这样补：
- <给 2-5 个和当前任务相关的最小样本示例，不要写成长表>
- 如果没有样本，可以先提供：任务描述 + 当前卡点 + 期望输出 + 禁止触碰的边界。
```

## 工作逻辑确认卡模板

正式生成任何 Prompt、Checklist、Loop、Agent 或 Skill 前输出，并等待用户确认。补齐必需信息只代表 Context Gate 通过，不代表用户已经确认工作逻辑。
确认前只输出确认卡，不输出正式 Prompt、Checklist、Loop 包、Agent 包、Skill 协议或任何执行指令。
确认必须严格：只有上一轮已输出确认卡，且用户明确回复“确认继续”“按这个逻辑生成”“可以生成正式产物”“生成吧”等授权表达，才算确认；补充路径、图片、链接或数据都不算确认。

```md
## 状态
- 当前阶段：WAITING_FOR_LOGIC_CONFIRMATION
- 停止原因：等待用户确认工作逻辑
- 下一步触发：用户明确回复“确认继续”或“按这个逻辑生成”

## 工作逻辑确认卡

如果没问题，请回复“确认继续”。如果要调整，请直接指出要改哪一项。
```
